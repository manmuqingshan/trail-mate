状态：**缺口补全候选已交付，待用户评审；未经批准仍不得编码**。日期：2026-09-15。

本文件保留发现问题与逐轮修正的历史证据。最终需求覆盖及G01–G23的定义位置见[交付审计](./22-文档交付审计与评审入口.md)；下表早期“待补/需复核”描述不单独作为最新交付结论。实际运行测试依然未执行，不作通过承诺。

## 1. 完成判据

每项关键行为必须有输入、合法性、所有者、结果、副作用、失败、重试、重启恢复及可观察验收；不适用的维度须说明原因。名词已有定义、章节存在或 Mermaid 可渲染都不能单独证明行为已闭合。

只有以下条件同时成立才可称“可提交编码前评审”：

1. 下表所有设计缺口都有确定候选和准确引用，无依赖实现者临场猜测的协议行为。
2. 基础协议、公共发现、设备接口、存储和交互没有相互冲突的定义。
3. 每条新增/修正规则有例子或判定明确的验收项。
4. 影响公开性、身份、版本、资源取舍的选择集中列给用户裁决。
5. 真实平台未验证事项如实分开，不以设计推演冒充运行结果。
6. 用户批准的具体版本与范围另行记录；设计完备不等于已经批准。

## 3. 证据与验证分层

| 层级 | 可证明什么 | 不证明什么 |
| --- | --- | --- |
| 文件/链接检查 | 文档存在、引用可达、编码可读 | 语义完整、可互操作 |
| 场景桌面推演 | 特定事件顺序有确定结果 | 硬件时序、存储实际耐久 |
| 静态字节向量 | 指定输入的预期编码与摘要可复核 | 整个协议已经实现 |
| 源码核查 | 当前接口事实与拟议接入点 | 未执行路径的运行正确性 |
| 实现测试 | 将来可验证具体代码行为 | 当前没有执行，不能虚报 |
