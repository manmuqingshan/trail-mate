状态：**待评审草案；不得据此提前开发**  
文档版本：`0.2.0-draft`；拟议线协议：`1`；记录模式：`1`  
关联：[设计入口](./README.md) · [交互设计](./02-交互设计.md) · [评审与验收](./03-评审与验收.md)

## 1. 规范地位与目标

本稿定义第三方可以独立实现的应用协议候选，不是 LXMF 官方注册标准，不声称与现有 geocaching 应用互操作。“必须/不得”为拟议合规要求；“建议”为默认策略；所有新设计等待用户批准。

本稿仍有设计缺口，不代表已经可直接启动编码。补全进度见[完备性审计](./09-设计完备性审计.md)；请求/取消/并发/耐久语义的补充契约见[生命周期与恢复](./10-请求生命周期与持久恢复契约.md)。

目标是经由 LXMF 完成面向公共网络的发布、查询、下载和目录复制。用户不指定读者；兼容终端无需作者邀请即可自动发现公开内容。协议不提供全网共识、可信时间、全球唯一目录或永久可达保证。

[公共发现与传播](./04-公共发现与传播.md)是本规范的组成部分，定义发现 announce、公共目录角色、sync 操作与网络分区恢复。只实现单点投递而没有公共发现和传播，不符合本功能要求。

## 2. 协议分层与端点

```text
用户意图 / 本地寻宝与地图投影
              ↓
本规范：请求账本、标点版本与目录语义
              ↓
LXMF：消息封装、验证、投递与交付事实
              ↓
Reticulum：身份、目的地、路径、Link / Resource
              ↓
可用接口和物理承载
```

1. 所有请求和响应都作为 LXMF 消息发往对方的 `lxmf.delivery` 目的地。
2. 端点以完整 16 字节 LXMF 目的地 hash 寻址；不能用显示名、无线节点号或作者 hash 代替。
3. 通过专用 `trailmate.geocache.directory` 服务 announce 自动发现公共目录，验证后请求 capabilities；普通 announce 不代表支持本协议。手工种子地址只用于发现入口恢复，不是玩家必须添加的收件人。
4. 公共目录的发现目的地与 LXMF delivery 目的地绑定同一 Reticulum Identity，完整规则见公共发现文档。显示名不决定身份。
5. 纯客户端声明操作 0；公共目录必须支持 [0,1,2,3,4]，即 capabilities/publish/query/get/sync。只接受提交、不向公众提供读取的端点不是公共目录。
6. 不支持本协议的 LXMF 客户端可能把消息显示成普通文本，甚至不响应；不得推断它支持某项操作。
7. 传播节点只转递 LXMF；目录查询和存储操作由最终应用接收方处理。
8. 不使用未经认证的裸广播承载内容，不允许第三方 reply_to。公共发现规则允许并要求有界的自动入口选择、查询与复制，不能退回私人分享模式。

## 3. 字节类型与规范编码

### 3.1 基本约定

`bin[N]` 为恰好 N 字节 MessagePack binary；`bin[0..N]` 为可变长度 binary；`str[N]` 为 UTF-8 字节数不超过 N 的字符串；`uint32` 范围为 0 至 4294967295。正文中 `<…>` 只是示意，不是可直接上网的字节。

所有数组位置固定、长度固定；可选值用 `nil` 占位，不能省去元素。下文 `null` 与 `nil` 均指 MessagePack nil。整数不能用浮点数或布尔值替代。v1 不允许应用载荷内出现 map、ext、float 或未定义类型。

以上限制只约束CUSTOM_DATA内应用信封与签名记录。外层标准LXMF仍使用自己的timestamp浮点数与fields map，不能为了CMP1修改标准LXMF布局。固定上游源码核对见13 §4。

### 3.2 规范 MessagePack 子集 CMP1

应用信封和签名记录使用同一规范编码 CMP1：

- 非负整数使用最短的 positive fixint / uint8 / uint16 / uint32 / uint64；不得用 signed 格式表示非负整数。
- 负整数使用最短的 negative fixint / int8 / int16 / int32 / int64。
- 数组使用最短的 fixarray / array16 / array32；字符串使用最短的 fixstr / str8 / str16 / str32；二进制使用最短的 bin8 / bin16 / bin32。
- 多字节整数和长度按 MessagePack 大端序编码；禁止冗余宽度。
- 字符串必须是有效 UTF-8，不接受过长 UTF-8、孤立代理项或非法字节。不得在接收后替换字符再验证。
- 不执行 Unicode 归一化；两个视觉相同但字节不同的字符串是不同的签名内容。作者编辑器可在签名前选择文字形式，转发者不得改写。
- 可见文本不允许 U+0000–U+001F 和 U+007F–U+009F，描述与提示额外允许 LF 和 TAB；输入 CR/CRLF 在签名前转换为 LF。
- 为保证每个合法公开记录能写入XML1.0 GPX，所有映射到可见XML文本的字段还必须拒绝U+FFFE与U+FFFF；代理项已由有效UTF-8/Unicode标量约束排除。不能接收后删去非法字符来使签名“通过”。这是草案字符约束的补充，既有ASCII静态向量不变。
- 除 schema 指定的 nil 外，不允许其他缺省；禁止尾随字节和连续多个顶层对象。
- 解码信封与内层记录分别限制嵌套深度为 8；数组元素总数每个信封不超过 2048。

接收方必须检查规范编码；可采用受限解析器检测非最短编码，或验证规范重编码等于原字节。后一做法不授权在设备上构造无界对象树。

### 3.3 最短编码边界对照

以下片段是类型头/标量示例，不是完整应用消息。长度字段指UTF-8字节数或binary长度，array长度指元素数。

| 逻辑值/长度 | CMP1头或完整标量hex | 拒绝的等值冗余形式 |
| --- | --- | --- |
| 整数127 | `7f` | `cc 7f` |
| 整数128 | `cc 80` | `cd 00 80` |
| 整数255 | `cc ff` | `cd 00 ff` |
| 整数256 | `cd 01 00` | `ce 00 00 01 00` |
| 整数65536 | `ce 00 01 00 00` | uint64冗余宽度 |
| 整数-32 | `e0` | `d0 e0` |
| 整数-33 | `d0 df` | `d1 ff df` |
| 空字符串 | `a0` | `d9 00` |
| str长度31/32 | `bf` / `d9 20`，后接字节 | str16用于长度32 |
| bin长度0/255/256 | `c4 00` / `c4 ff` / `c5 01 00` | bin16用于长度255 |
| array长度15/16 | `9f` / `dc 00 10` | array16用于长度15 |
| nil | `c0` | 缺元素、空bin、false都不是nil |

这些编码与固定MessagePack格式规范对齐；“所有字段必须最短、应用内禁止map/float/ext、拒绝尾随字节”是本协议额外的确定性约束。具体完整记录和请求向量见examples/SIGNED-VECTOR.md及对应JSON；本表不代替完整操作验收。

## 4. LXMF 承载

| 外层字段 | v1 要求 |
| --- | --- |
| `FIELD_CUSTOM_TYPE (0xFB)` | MessagePack str，精确为 `trailmate.geocache`，区分大小写 |
| `FIELD_CUSTOM_DATA (0xFC)` | MessagePack bin，内容为 CMP1 编码的应用信封 |
| `FIELD_CUSTOM_META (0xFD)` | v1 不发送；接收时忽略，不得影响协议含义 |
| title | 固定可读标识 `Trail Mate Geocache v1` |
| content | 请求为 `Geocache request`，响应为 `Geocache response`；不重复坐标或正文 |

title/content 不参与应用语义判断；接收方不得依赖它们匹配字符串来路由。发送方仍须遵守上表以避免不必要的开销。外层 LXMF 标准字段（例如票据）由 LXMF 处理；不得夹带第二份本协议载荷或用附件绕过上限。

解压和验证 LXMF 后，先检查 `CUSTOM_DATA` 类型和长度，再解析 CMP1。只有外层发送方身份可验证、签名有效，才能执行操作或接受响应。未知来源公钥尚未取得时保持“等待身份验证”或丢弃，不先执行再补验证。

上游保留 `CUSTOM_TYPE/CUSTOM_DATA` 供应用协议嵌入；本稿使用这些字段，不分配新的 LXMF 核心字段。[LXMF 字段定义](https://raw.githubusercontent.com/markqvist/LXMF/master/LXMF/LXMF.py)

## 5. 应用信封

### 5.1 请求

```text
[wire_version, kind, operation, request_id, response_budget, body]
```

| 位置 | 字段 | 类型与语义 |
| --- | --- | --- |
| 0 | wire_version | v1 为整数 1 |
| 1 | kind | 请求为整数 0 |
| 2 | operation | 0 capabilities；1 publish；2 query；3 get；4 sync |
| 3 | request_id | CSPRNG 生成的 `bin[16]`，同一逻辑请求重试保持不变 |
| 4 | response_budget | 整数 512..8192；允许响应的 `CUSTOM_DATA` 原始字节上限 |
| 5 | body | 对应操作定义的数组 |

### 5.2 响应

```text
[wire_version, kind, operation, request_id, status, body]
```

版本、操作和请求 ID与请求关联；响应 kind=1（请求为 0），status 为第 13 节定义的整数。响应回到已验证的请求 LXMF 源地址，不读取正文中的地址。v1 无第三种通知信封、无无请求推送、无应用响应 ACK。

每个已接受请求恰有一个终态应用响应，重发可以产生重复投递。query/sync 的每一页都是独立请求；不把多条响应拼成一页。外层 LXMF hash 可以在重发时不同。

### 5.3 响应匹配

响应只有满足以下条件才可改变请求状态：外层发送方是请求的目标目的地、接收方是原请求方、版本/操作/请求 ID 匹配、未超过该请求预算、状态与正文结构合法。未知请求 ID 的响应不得导入标点、触发发布或发送错误响应。

对协议错误的响应也不回复，避免循环。对可识别且可信的畸形请求按第 13 节响应；无法安全读取请求 ID、版本框架或认证失败时直接丢弃并本地记录原因。

## 6. 稳定身份、记录与签名

### 6.1 三类标识

| 标识 | 长度 | 含义 |
| --- | --- | --- |
| `cache_id` | 32 字节 | 一个藏宝点，跨版本和来源稳定 |
| `revision_hash` | 32 字节 | 一份精确签名记录的内容版本 |
| `request_id` | 16 字节 | 一个请求，按请求方和目标方作用域去重 |

外层 LXMF 消息 hash 仅用于底层消息关联，不能替代以上任何一个。

### 6.2 CacheRecord 固定数组

```text
[schema, author_public_key, creation_nonce, revision, previous_hash,
 state, latitude_e7, longitude_e7, name, description, hint,
 difficulty_x2, terrain_x2, container_size, created_at, updated_at]
```

| 位置 | 字段 | 类型 / 限制 |
| --- | --- | --- |
| 0 | schema | 整数 1 |
| 1 | author_public_key | `bin[64]`，Reticulum 公共身份：X25519 公钥 32 字节后接 Ed25519 公钥 32 字节 |
| 2 | creation_nonce | CSPRNG 生成的 `bin[16]`；创建后不变 |
| 3 | revision | uint32，1..4294967295；递增，不允许回绕 |
| 4 | previous_hash | revision=1 必须 nil；否则必须 `bin[32]` |
| 5 | state | 0 active，可寻找；1 disabled，暂不可寻找；2 archived，作者撤下 |
| 6 | latitude_e7 | 整数，-900000000..900000000；WGS84 纬度乘 10^7 |
| 7 | longitude_e7 | 整数，-1800000000..1799999999；WGS84 经度乘 10^7，+180°归一为 -180° |
| 8 | name | 非空 `str[96]`，不能全部为空白 |
| 9 | description | `str[2048]`，可为空；纯文本 |
| 10 | hint | `str[512]`，可为空；纯文本，非密码学隐藏 |
| 11 | difficulty_x2 | 整数 2..10，表示 1..5 星，每半星一个等级 |
| 12 | terrain_x2 | 整数 2..10，表示 1..5 星，每半星一个等级 |
| 13 | container_size | 0 未说明；1 微型；2 小型；3 中型；4 大型；5 其他实体容器 |
| 14 | created_at | 0..253402300799，UTC Unix 秒；0 为作者时间未知 |
| 15 | updated_at | 同上；0 为未知 |

时间是作者声明，不影响版本胜负或签名有效性；时钟回退不导致内容被自动拒绝。创建时确定的公钥、nonce、created_at 不得在后续版本改变。观察到同 ID 的 created_at 不一致属于内容链冲突。

坐标从用户输入量化时采用最接近整数、恰好半单位向远离零方向取整。经度归一后再量化，并再次保证 +180°映射到 -180°。v1 没有高程、隐藏实际位置、路线或多阶段子点。

`record_bytes=CMP1(CacheRecord)`，总长度必须 ≤4096 字节。字段上限与总上限同时生效，不能按总长度放宽单字段。

### 6.3 派生与签名公式

下面 ASCII 常量中的 `\0` 表示一个真实的 0x00 字节；拼接没有额外长度、换行或空格。SHA-256 输出使用全部 32 字节。

```text
cache_id = SHA256(ASCII("trailmate.geocache/id/v1\0")
                  || author_public_key || creation_nonce)

revision_hash = SHA256(ASCII("trailmate.geocache/revision/v1\0")
                       || record_bytes)

author_signature = Ed25519.Sign(author_signing_private_key,
                   ASCII("trailmate.geocache/sign/v1\0") || record_bytes)

SignedCache = [record_bytes: bin[1..4096], author_signature: bin[64]]
```

使用普通 Ed25519，不使用 Ed25519ph 或自行预哈希后签名。校验器从记录公钥的后 32 字节取签名公钥，验证完整带域字节串；同时验证公钥表示合法。身份 hash 可以按 Reticulum 派生供显示，但不作为 `cache_id` 的替代。

采用 Reticulum 现有公共身份布局和签名算法，不引入新账户密钥。[Reticulum Identity 实现](https://raw.githubusercontent.com/markqvist/Reticulum/master/RNS/Identity.py)

### 6.4 验证顺序

1. 检查外层 LXMF、载荷上限和 CMP1 信封。
2. 检查 `SignedCache` 数组、记录字节及签名长度。
3. 有界解析原始记录，验证类型、范围、规范编码和模式版本。
4. 验证作者公钥和作者签名；失败不能进入可信对象存储。
5. 从原始字节计算 ID 和版本 hash，核对请求、响应和已知版本关系。
6. 按版本规则接纳或隔离，再原子持久保存事实；成功后才能投影到“已下载”。

转发者必须保留 `record_bytes` 与签名原样。外层源身份和内层作者允许不同；二者分别显示。LXMF 外层签名不证明转发者就是原作者。[LXMF 消息签名实现](https://raw.githubusercontent.com/markqvist/LXMF/master/LXMF/LXMessage.py)

## 7. 版本、冲突与撤下

### 7.1 普通版本接纳

- 无本地版本：允许接纳任意有效 revision 的完整快照；revision>1 时标记历史未验证完整。
- 同 ID、同 revision_hash：同一版本，不创建第二份标点。
- 同 ID、同 revision、不同 revision_hash：保存冲突证据，冻结此 ID 的自动当前版本选择。
- 相邻新版本：若 previous_hash 不等于已知前一版本 hash，则冲突；正确衔接才更新。
- 跨越多个版本：若没有已知冲突，允许有效作者签名的新版本成为“本地已知最新”，但历史完整性保持未知。previous_hash 必须在可获得前驱时补查，不能伪称整链已验证。
- 旧版本不得回退当前版本。校验旧版本也可能揭示历史分叉，此时转为冲突。
- 不同来源的相同对象合并来源记录；不得改变作者字段。

保留已接受版本的 `(revision, hash, previous_hash, state, created_at)` 元数据直到用户明确删除该点及历史。目录还必须保留同步日志和冲突证据需要的正文。每份记录均核对所有已知相邻前驱、后继与终止状态，不能只比较当前头部。同 record_bytes 的两个有效签名仍是同内容。

元数据可以支持本地防回退，但不能代替原作者签名正文作为对外冲突证明。若涉及历史正文已清理，先记为“历史待核实”，保留原当前选择并停止该点自动升级，尝试按已知hash找回旧签名对象；只有两份相关记录均完成独立验签才能升级为可传播的已证实冲突。不得把元数据重新编码并假装带有作者签名。目录query暂不输出这类待核实点；get latest 返回503 temporarily_unavailable，精确get仍按已有正文提供。待核实不是永久确认冲突，恢复证据后按普通版本/冲突规则处理。

### 7.2 冲突处理

v1 不设计分支合并或密钥仲裁。一旦确认版本链矛盾，冻结该 ID的自动当前选择，后续高版本不能解除。冲突 ID不进入普通 query；get latest 返回 409。具体签名版本仍可按 hash 读取并标记冲突；公共 sync 必须提供足以验证冲突的签名对象引用，不能因 query 隐藏而停止传播证据。

用户可查看最后使用的副本，但必须显示冲突；不得把“最后收到”解释成真相。v1 的恢复方案是作者停止使用旧 ID，创建新 ID 并通过人工说明迁移；自动冲突解决留待新协议设计。这是待评审的明确取舍，不是遗漏恢复流程。

### 7.3 作者状态

`active ↔ disabled` 允许互转；`active/disabled → archived` 允许；`archived` 是 v1 终止状态，不允许再次 active/disabled，也不允许追加其他版本。若观察到 archived 后的任何更高版本，作为链冲突处理，即便先收到高版本、后收到旧 archived 版本也一样。

archived 仍携带完整签名记录，属于状态声明，不是全网内容擦除。旧副本、未收到撤下的来源、签名历史都可能继续存在。删除本地副本不能生成 archived 记录。

版本号用尽、作者密钥丢失或泄露时，v1 不提供同 ID 的转移恢复。必须停止继续签发，另建身份/ID并人工迁移。备份身份与同一身份的多设备写入纪律见交互文档。

## 8. capabilities（操作 0）

请求 body：空数组 `[]`。无需预先协商即可发送，建议 response_budget=8192；能力响应实际必须 ≤512 字节。

成功 `200` body：

```text
[supported_wire_versions, supported_record_schemas, operations,
 max_data_bytes, max_record_bytes, max_query_items,
 cursor_ttl_seconds, dedup_ttl_seconds, publish_policy, source_name,
 directory_role, sync_ttl_seconds]
```

| 字段 | v1 值 / 类型 |
| --- | --- |
| supported_wire_versions | 严格递增、不重复的整数数组，v1 包含 1，最多 8 项 |
| supported_record_schemas | 同上，v1 包含 1 |
| operations | 公共目录固定 [0,1,2,3,4]；纯客户端为 [0] |
| max_data_bytes | 固定 8192；是应用载荷接收上限，不是无线包大小 |
| max_record_bytes | 固定 4096 |
| max_query_items | 支持 query 为 1..64，否则 0 |
| cursor_ttl_seconds | 支持 query 时为 60..604800，否则 0；建议 604800（7 天） |
| dedup_ttl_seconds | v1 固定 2592000（30 天），从首次接受请求起计 |
| publish_policy | 0 不接收（纯客户端）；2 接受公开记录及转交；1 在 v1 未分配 |
| source_name | `str[96]`，显示用途，能力响应总长仍须 ≤512 |
| directory_role | 0 纯客户端；1 公共目录 |
| sync_ttl_seconds | 公共目录固定 2592000（30 天最大寿命，实际剩余期由响应给出）；纯客户端为 0 |

公共目录必须开放全部五个操作且 policy=2，query/get/sync 不得要求读者成为联系人、成员或得到作者邀请。纯客户端只声明操作 0、policy=0，query/sync 相关能力值为 0。

能力不保证永久可用：目录可按反滥用、容量和资源预算拒绝，必须返回明确错误。能力缓存建议 24 小时，不匹配时自动重新检查一次并退避。反滥用不能变成读者私人邀请制。

## 9. publish（操作 1）

请求 body：`[signed_cache]`，一次仅一个完整版本，不允许批量或部分字段补丁。建议 response_budget=512。

成功 `200` body：

```text
[cache_id, submitted_revision, submitted_hash, disposition,
 current_revision, current_hash, current_state]
```

`disposition=0` 表示本次保存并设为已知当前；`1` 表示相同当前版本已存在。其余字段分别描述提交对象与接收方在处理时的已知当前，必须相等匹配。v1 不用成功状态接受过时提交：如果当前已更高，返回 `409 stale_revision`，防止把保存旧副本显示成“更新成功”。

接收流程：身份/模式/签名验证 → 反滥用与配额 → 版本检查 → 将对象、公共索引、同步日志和请求结果作为一个可恢复事务提交 → 生成成功响应。

有效作者记录若构成已证实冲突，409 version_conflict 表示不把它接纳为正常当前版本；目录仍须持久保存充分的签名证据、隔离状态和同步引用。这是冲突保护的明确副作用。无效签名、无效格式或单纯过时且不构成冲突的提交不进入公共变化日志。

`200` 保证记录已持久保存并进入公共 get、适用状态的 query 和 sync，重启可恢复；不得先确认再放进不可见的私人审核区。它不代表全部目录已复制。接纳记录至少保留 30 天并履行所有未到期快照/日志正文承诺，之后才可按容量政策移除；确认是当时的公开接纳事实。

已生成的成功响应重放时必须保持其原业务结果，不能用今天的新 current 替换原结果。要了解当前状态，客户端另发 get。

相同请求重放不延长对象保留期；新request_id提交同一当前版本且得到disposition=1，是新的接纳确认，须从新接纳时刻保证至少30天保留，但不追加重复变化日志。完整并发与恢复规则见10 §7–9。

公开发布进入自动复制流程：目录经 sync 拉取其他目录的新记录，客户端可自动向第二公共入口提交同一签名对象提高可用性。用户不选接收者。未接纳时明确拒绝，接纳后公开提供，不设计悬置的私人审核中间态。传播调度见公共发现文档。

## 10. query（操作 2）

### 10.1 请求

```text
[bbox, state_mask, author_key_hash, page_limit, cursor]
```

| 字段 | 定义 |
| --- | --- |
| bbox | `[south_e7, west_e7, north_e7, east_e7]`；纬度边界同记录，south≤north；经度边界允许 -1800000000..1800000000，west≤east |
| state_mask | 整数 1..7；bit0 active，bit1 disabled，bit2 archived；默认建议 3 |
| author_key_hash | nil 或 `bin[32]`；非 nil 时等于 SHA256(author_public_key)，使用完整公钥作输入 |
| page_limit | 1..64 且不超过来源宣告上限；建议 20 |
| cursor | 首次 nil；后续为来源发出的 `bin[1..64]` |

区域两端包含边界。+180°边界等价覆盖记录规范化后的 -180°点；跨日期变更线的区域由客户端拆成两个 bbox 查询，以 cache_id 去重。全世界用 `[-900000000,-1800000000,900000000,1800000000]`，来源仍可按负载拒绝。

v1 不定义圆形半径、距离排序或全文搜索；“附近”由客户端选择 bbox 后在本地计算距离。过滤在当前已知版本上执行，不能把同一 ID 的多个历史版本作为多个摘要。

### 10.2 响应

成功 `200` body：`[snapshot_id, summaries, next_cursor, remaining_ttl_seconds]`。

- snapshot_id 是来源生成的随机 `bin[16]`，只在该来源内解释。
- summaries 是 0..page_limit 项的 Summary 数组。
- next_cursor 为 nil 或 `bin[1..64]`。nil 明确结束，不提供不可靠的全网总数。
- remaining_ttl_seconds 是响应生成时该快照剩余秒数；传输延迟后不能当成仍有那么久。

Summary 固定结构：

```text
[cache_id, revision, revision_hash, state, latitude_e7, longitude_e7,
 name, difficulty_x2, terrain_x2, container_size, signed_cache_bytes]
```

字段类型同记录，`signed_cache_bytes` 是 `CMP1(SignedCache)` 的准确字节长度，1..4166。摘要是**来源签名的消息中的声明**，不是独立作者签名。拿到完整对象后必须逐项匹配上述摘要字段；不匹配时保留“来源摘要不一致”证据，不把摘要升级为已验证详情。

### 10.3 快照、顺序和字节预算

1. 首次查询固定匹配集合及各项 revision_hash，按 cache_id 原始字节无符号字典序递增。
2. 后续游标绑定：请求方、接收端点、wire_version、bbox、过滤条件、page_limit、response_budget、快照和下一位置。改变任一参数必须重新查询。
3. 同一快照内更新不会导致重复或漏项；来源必须在有效期内保留快照所需摘要和精确版本正文，或明确使游标失效。
4. 服务重启可以恢复快照，也可以使旧游标统一 `410 cursor_expired`；不得把旧游标重新解释成新快照。
5. 先按完整响应 CMP1 字节数和 page_limit 取可容纳的最大前缀；必须计入信封、游标和数组开销。
6. 最小预算仍放不下一条待返回摘要时，返回 `413 response_too_large`；不能返回空列表加同一游标形成死循环。
7. 非末页必须有至少一项并前进；空集合返回空列表、nil 游标。
8. 查询建议预算 2048 字节；终端必须支持 v1 的 8192 字节接收能力，不能借此无限分配内存。
9. 已返回摘要只对该快照有效。签名对象后续不再可取时，get 返回明确错误；不能默默替换版本。

不同请求 ID 重用同一未过期游标也应得到同一页和后继位置；过期后按 410 返回。相同请求 ID 的历史重放按去重账本，可能返回已过期快照的原页；下一页过期时重新查询。

目录中缺失某个点不代表作者撤下；可能是过滤、来源移除、副本缺失或冲突隔离。已下载点的状态更新应对其 ID 执行 get，不能只依赖区域查询差分。

## 11. get（操作 3）

请求 body：`[cache_id, wanted_hash, known_hash]`。

- cache_id 为 `bin[32]`。
- wanted_hash 为 nil 表示来源当前已知最新，否则为精确 `bin[32]`。
- known_hash 为 nil 或客户端已持久保存的版本 hash；wanted_hash 非 nil 时 known_hash 必须 nil。
- 建议 response_budget=8192；一次只取一个点，不进行 v1 应用层分片。

成功 `200` body：`[signed_cache, is_current, has_conflict]`；后两个字段为整数 0/1，不是布尔类型。客户端必须重新计算对象 ID/hash。精确 get 必须与 wanted_hash 完全一致。

当 wanted_hash=nil 且无冲突，来源当前 hash 等于 known_hash 时返回 `304` body：`[cache_id, revision, revision_hash, state]`。只有本地确实持有对应已验证对象才可显示未变化，不能把 304 当成一次下载。

latest 只代表该来源处理时的已知最新，不代表全网最新。精确版本可以是历史版本，`is_current=0`；已知冲突时精确 get 允许返回该版本并设 `has_conflict=1`。客户端自己的冲突证据不因来源返回 0 被清除。

未知 ID 返回 `404 not_found`。已知 ID 但精确正文不在保留范围返回 `404 revision_unavailable`。latest 遇到已知冲突返回 `409 version_conflict`。archived 对象正常返回 200/304，不用 404 伪装撤下。

客户端收到比本地旧的有效对象可以保存为历史或忽略正文，但不得回退当前指针。下载多点时逐点独立确认、允许部分成功；批量完成是客户端汇总，不是协议事务。

## 12. 重试、幂等与持久性

### 12.1 两层去重

LXMF 层以自身消息标识处理底层重复；应用层另用以下作用域：

```text
request_key = (verified_source_destination, local_destination,
               protocol_type, wire_version, request_id)
request_fingerprint = SHA256(original_CUSTOM_DATA_bytes)
```

同 request_key、同指纹：重放同一个已持久记录的终态响应 `CUSTOM_DATA`，外层 LXMF 可重新打包。不同指纹：`409 request_id_reused`，不得执行新内容；包括改变 operation、预算或 body。

request_id_reused 是由原账本导出的拒绝，不能替换原指纹或原结果，也不为攻击者每种错误变体创建永久条目；错误响应仍须限流。

接收该错误的客户端不能据此终结另一份原合法请求；该错误未携带指纹，按10 §3标记关联异常并保留原请求，后到的合法200仍可确认。任意同请求的不同终态结果不得按到达时间覆盖首个合法结果。

尚在处理的相同请求合并，不启动第二次写入。请求结果至少保留 30 天；从首次接受请求起计，重试不能延长保留期。接纳新请求前必须预留结果空间，不提前淘汰窗口内已接受请求。资源不足时仅在能持久保留拒绝结果的情况下返回 503/429；连拒绝结果也无法持久记录时安全丢弃，不执行操作，由发送方保持未确认。已经持久保存的重复请求优先重放。

30 天后相同请求可能重新执行只读操作；publish 仍受对象幂等与版本单调性保护，但历史结果可能变成 stale。协议不承诺跨任意时间的“恰好执行一次”。

### 12.2 临时错误与重试身份

对已接受请求产生的错误同样是终态结果，窗口内重试相同 ID重放原错误。希望重新评估 429/503/收录政策变更/游标重开时，客户端必须创建新 request_id。尚未得到终态、无法判断是否处理过时才沿用原 ID。对无法接纳或不可信畸形输入的安全丢弃不承诺产生响应。

同一操作重发保持 CUSTOM_DATA 完全相同，包括 response_budget；改变下载版本、来源或查询参数视为新请求。来源不同须创建新请求并独立跟踪结果。

### 12.3 发送方建议调度

- LXMF 自己还在发送时不叠加应用层重发；先让其进入可识别的结果或等待状态。
- direct 建议在 5 分钟无应用响应后提示“尚未确认”；允许一次应用重试，之后由用户决定。
- propagated 建议在 24 小时无应用响应后提示“尚未确认”；默认不自动重发，由用户决定。
- 用户停止等待只停止本机新重试；不能撤销已进入网络或已执行的 publish。
- 未完成请求关联记录建议持久保留 30 天；停止等待的请求也保留。期间迟到结果标为“迟到确认”，不能自动重启取消的查询分页或删除任务。
- 记录过期后到达的未知响应只保留有限诊断信息，不自动导入。

这些时间是同一入口的请求调度建议，不是消息 TTL，也不影响公共发现文档规定的入口故障转移。用户只发起一次公开发布，应用可自动联系不同目录并分别追踪。更长断网可能让请求晚于预期执行；确认页必须说明。

### 12.4 持久化顺序

请求执行、对象接受、公共索引、同步日志和终态结果必须在掉电后恢复到一致状态。不得先发送成功再落盘。LXMF 已接收消息进入可恢复的应用处理路径，不能因聊天投影不显示就丢弃请求。

收到响应后，先持久保存有效对象与请求结果，再显示“已下载”。空间不足时保持旧版本并显示本地保存失败，即使对方已返回 200。

## 13. 状态码与错误正文

状态码是本协议整数，借用熟悉的编号以便阅读，不代表 HTTP 请求。

| status | token | 场景 / context |
| --- | --- | --- |
| 200 | 不使用错误正文 | 操作成功，按各操作正文 |
| 304 | 不使用错误正文 | 仅 get，未变化 |
| 400 | malformed_request | 可关联但信封/正文/规范编码/参数非法；nil |
| 400 | invalid_cursor | 非法游标、绑定不匹配；nil |
| 403 | forbidden | 发布违反公开收录政策或请求被反滥用规则拒绝；nil，不表示需要私人读者邀请 |
| 404 | not_found | 本来源没有该公开ID；nil，不用来隐藏已接纳的私人读者限制 |
| 404 | revision_unavailable | 精确版本正文不可提供；nil |
| 409 | request_id_reused | 请求 ID 对应不同字节；nil |
| 409 | stale_revision | publish 提交过时；`[current_revision,current_hash,current_state]` |
| 409 | version_conflict | 已知作者链冲突；nil |
| 410 | cursor_expired | 快照过期或重启失效；nil |
| 410 | sync_reset_required | 公共同步游标失效、日志过期或 epoch 改变；nil |
| 413 | request_too_large | 入站应用数据超限；`[8192]` |
| 413 | record_too_large | 内层记录超限；`[4096]` |
| 413 | response_too_large | 合法请求预算容不下响应；`[required_data_bytes]` |
| 422 | invalid_record | 记录类型、状态或字段约束非法；nil |
| 422 | invalid_signature | 作者签名/公钥验证失败；nil |
| 426 | unsupported_version | 不支持信封版本或记录模式；`[supported_wire_versions,supported_record_schemas]` |
| 429 | rate_limited | 超过频率、流量或提交配额；nil |
| 501 | unsupported_operation | 不实现此操作；nil |
| 503 | temporarily_unavailable | 无法执行/持久化/保留结果；nil |

所有错误 body 精确为 `[token, retry_after_seconds, context]`。token 为表内 ASCII str；retry_after_seconds 为 nil 或 1..604800 的整数，仅 429/503 可非 nil；其余必须 nil。错误不携带远端可执行文本或私密诊断。

### 13.1 操作与错误适用矩阵

通用错误集合为：malformed_request、forbidden、request_id_reused、request_too_large、response_too_large、unsupported_version、rate_limited、unsupported_operation、temporarily_unavailable。它们仍须符合对应场景，不能随意选择同义码。capabilities成功正文必须≤512，因此对合法预算的capabilities不应产生response_too_large。

| operation | 通用集合之外的允许错误 | 明确不允许的结果 |
| --- | --- | --- |
| capabilities | 无 | 304、not_found、version_conflict、游标错误 |
| publish | record_too_large、invalid_record、invalid_signature、stale_revision、version_conflict | 304、not_found、revision_unavailable、游标错误 |
| query | invalid_cursor、cursor_expired | 304、invalid_signature（请求没有签名对象）、单点not_found |
| get | not_found、revision_unavailable、version_conflict | 游标错误、stale_revision、invalid_signature（请求无对象） |
| sync | invalid_cursor、sync_reset_required | 304、cursor_expired（必须用同步重建错误）、stale_revision |

get的revision_unavailable仅用于指定wanted_hash；version_conflict用于latest，精确版本仍可按正文规则返回。query无匹配应为200空集合，不是404。无入站操作能力的纯客户端对于publish/query/get/sync回501，而不是伪造无目录结果。

本机收到坏签名get响应属于本地验证失败和来源违规，不向原来源发送invalid_signature响应；后者仅是接收publish请求的错误。无法执行密码学验证与签名确实无效分开：前者是本地资源/能力问题，不能报告作者伪造。

### 13.2 语义检查优先级

请求按12文档§8顺序处理：安全外层/预算→信封→去重→操作/正文→提交对象格式与签名→策略/资源→版本/存在/游标→耐久结果。若多个条件同时非法，返回首个确定错误；资源防护可以在解析前安全丢弃，不为制造详细错误继续分配。

未知记录schema在publish中以426表示；已知schema但长度/字段/规范编码错误以422表示；签名检查只有在结构正确后进行。响应必须校验status/token/context组合与操作一致；不匹配时记录来源协议违规，不将其当成用户任务成功或远端合法拒绝。

错误响应必须 ≤512 字节且不超过有效请求预算。预算本身非法或缺失但安全可关联时用 ≤512 字节错误响应。对过大、无法验证或无法安全解析的载荷允许直接丢弃，不能为了回复继续分配攻击者声明的大小。

不支持的信封版本只有在能安全识别本稿六元素框架、kind=0、请求 ID 与操作时才用 v1 格式回 426；无法识别时丢弃。客户端允许把匹配来源和请求 ID 的该 v1 426 当成版本协商失败。其他响应必须严格匹配原版本。

## 14. 资源上限与拒绝策略

| 项目 | v1 上限 / 默认 |
| --- | --- |
| 解码后的 CUSTOM_DATA | 8192 字节，所有端点必须能有界接收 |
| CacheRecord 字节 | 4096 |
| CMP1(SignedCache) 字节 | 4166（4096 记录 + bin 包装 + 64 签名 + 数组包装） |
| 响应预算 | 512..8192；capabilities 8192 / publish 512 / query 2048 / get 8192 为发送建议 |
| 每页项目 | 1..64，受能力与字节预算共同限制 |
| 游标 | 1..64 字节 |
| 每个来源同时在途请求 | 客户端建议 1；接收方按容量限流 |
| 用户一次选择下载的点 | 界面建议最多 20，逐个请求，可分批 |

应用上限不包含 LXMF 标准开销、ticket/stamp、加密和链路头，因此不能直接宣称是空口流量。压缩后的大小不能绕过解压后的上限。LXMF 支持经 Link/Resource 传输较大消息；本协议仍不自建无线分包。[LXMF 消息传输实现](https://raw.githubusercontent.com/markqvist/LXMF/master/LXMF/LXMessage.py)

端点必须限制入站 LXMF resource/解压预算、排队条数、签名验证速率、来源磁盘配额和未完成快照数。具体设备值在能力核查后制定，达到限制明确拒绝，不能以大对象局部变量消耗 ESP 任务栈。本稿不宣称当前设备已有 8 KiB 处理能力。

若设备做不到 v1 上限，应不宣告该版本并保持功能不可用；不得静默截断 description、改签名对象或只实现不能互通的同名 v1。

## 15. 信任、隐私与服务策略

1. LXMF 外层认证与作者签名均有效才接受对象；认证不等于私人授权，任何兼容端点均可读取公开目录。签名不证明现实坐标准确。
2. 合法签名也可能是垃圾内容。目录可用发布反滥用、速率限制和存储配额，不能限制只有作者好友可看到。
3. v1 公开记录没有接收者限制；保密聊天地址不使公开标点变成私密标点。发布前说明可转发和不能全网撤回。
4. query 的区域暴露给自动选择的公共目录；首次启用公共发现时说明。默认选择地图区域，不自动上传当前位置或轨迹。
5. 目录摘要可被来源遗漏、歪曲或保留旧值；完整对象验签后才信任作者内容，仍不保证全网最新。
6. 响应只发给认证请求者，限制预算和频率；不提供可反射到第三方的大响应地址。
7. hint 是明文内容，界面“展开提示”只是避免剧透；不能标注为加密谜底。
8. 本协议消息通过独立业务投影展示，不制造聊天未读风暴；底层 LXMF 持久接收与去重仍须复用现有机制。
9. v1 不提供好友定向分享操作。目录通过公共发现和 sync 自动复制；客户端自动查询公共目录但只按用户动作下载正文。公开可见不等于向所有设备强制下载所有全文。

## 16. 兼容和升级

协议标识 `trailmate.geocache` 保持稳定；wire_version 和 record schema 独立版本化。v1 固定数组长度，不忽略额外字段、不默许未知枚举。将来新增字段、操作语义、签名算法或受限访问模型必须升版并协商，不能靠 CUSTOM_META 偷渡。

v1 未识别协议类型不执行；能识别类型但不支持版本时按 426 规则处理。更新客户端可以并行支持多个版本，但必须按对象原字节验签，不通过“升级转换”冒充作者发布新版本。
