# 02：界面能力目录与稳定契约

## 用途与边界

本目录是主题接口的业务基线，只覆盖 ESP32 下的用户可见 UI。它根据当前 `app_catalog_builder.cpp` 的应用目录、`ScreenRegistry`、`screen_240x320`、手表页面、ESP32 target/profile 绑定以及各页面的已定义路由整理而成，覆盖当前 ESP32 固件已经向用户暴露的界面能力。若需要确认每项能力在当前仓库的实际页面、嵌入视图、UX Pack 与源码入口，请先阅读 [13：当前 UI 源码盘点与解耦改造地图](./13-当前UI源码盘点与解耦改造地图.md)；本文件不把拟议的主题 `route_id` 误写成已经存在的 C++ 路由。

它不是“每个目标设备一定都有这些菜单项”的承诺。是否可用由固件目标、编译选项、硬件能力和现有 UX Pack 决定；主题只能呈现当次会话中固件已宣布为可用的能力。实际实施时，应由固件中的能力注册表生成机器可读清单，并让本表成为该清单的中文说明和测试基线。

## 稳定命名规则

- `capability_id` 使用小写英文点分命名，表达用户价值，例如 `chat.conversation`。
- `route_id` 使用能力前缀，例如 `chat.compose`、`settings.option_detail`。
- `action_id` 使用“能力.动词”，例如 `chat.send`、`extensions.install`。
- `slot_id` 使用“路由.语义部件”，例如 `chat.compose.send`。
- 已发布的 ID 只能弃用，不能重用或改变含义；显示文案、图标名和布局名称不是稳定 API。
- 一个主题只依赖 ID 与字段 Schema，不能依赖 C++ 类名、文件路径、LVGL 对象名、英语源文案或像素坐标。

## 必需槽位清单

这里的“必需槽位”不是一个抽象标签。它是每条 `route_id` 的结构性契约：布局校验器要求这些 slot 在已验证布局中**可达且恰好出现一次**；与 slot 关联的动作还必须在该 target/profile 的触控、键盘或编码器输入模型中可达。主题不能删除、合并、改名、用无动作装饰替代，或把危险确认动作映射到取消动作。

本节给出人可审查的完整槽位族目录。正式实现中，固件构建会为每个 target/profile 生成 `slots.json`（供 SDK/文档使用）及等价的二进制契约记录（供设备使用）。生成器以 [13：当前 UI 源码盘点与解耦改造地图](./13-当前UI源码盘点与解耦改造地图.md) 中的启动、AppCatalog、`PageKind`、手表、蜂窝和 overlay 源码映射为输入；它输出的是某 target 当前实际可达 route 的精确集合。profile 可以增加硬件专属 slot，但不能从已可达 route 删除本节列出的必需语义。

### 槽位校验规则

| 规则 | 校验结果 |
| --- | --- |
| 一个必需 slot 在页面布局中出现一次 | 通过；可放在 row、column、grid、stack、tabs 或允许的 overflow 容器中。 |
| 必需 slot 缺失、重复或位于不可达容器 | 拒绝该 route；对外部主题按完整 profile 拒绝启用。 |
| 必需动作 slot 没有匹配 action、可读标签/替代文本或输入可达路径 | 拒绝该 route。 |
| `confirm`/`cancel`、`send`/`cancel`、`apply`/`cancel` 等语义被调换 | 拒绝该 route，并给出固定契约错误码。 |
| 固件把能力标为不可用 | slot 不会出现在当次 `available_capabilities` 的必需列表；主题不能自行补出可点击入口。 |
| 同一主题声明多个 target/profile | 对每个声明 profile 单独验证完整 route 和 slot 集合；一个 profile 的成功不能代表另一个 profile。 |

## 页面契约示例：聊天编辑页

下面示例说明主题实际依赖的语义，而非要求把业务代码序列化进主题：

```yaml
capability_id: chat.compose
route_id: chat.compose
required_slots:
  - chat.compose.title
  - chat.compose.editor
  - chat.compose.send
  - chat.compose.cancel
  - chat.compose.delivery_status
optional_slots:
  - chat.compose.ime_switch
  - chat.compose.symbol_picker
  - chat.compose.emoji_picker
actions:
  - id: chat.edit_draft
    kind: text_input
  - id: chat.send
    kind: primary
  - id: chat.cancel_compose
    kind: secondary
invariants:
  - send_and_cancel_are_reachable
  - cancel_preserves_draft
  - back_in_editor_deletes_text_before_navigating
```

主题可定义 `chat.compose.send` 是顶栏图标、底部主按钮或紧凑溢出菜单中的项目，只要在当前输入模式下仍可达、拥有可读标签/替代文本，且不会与 `chat.cancel_compose` 混淆。

## 目标差异如何表达

能力目录分为“可声明”和“当前会话可用”两层：

- 固件目录定义所有可能的稳定 ID；本文件即该层说明。
- 启动后，UX Pack 和运行时能力计算生成 `available_capabilities`；主题只会收到这一集合。
- 某能力不可用时，主题不会获得对应动作。主题可以显示固件提供的“此设备不支持”说明，但不能伪造可点击入口。

建议主题清单使用 `supported_ux_packs` 与 `supported_layout_profiles` 显式约束目标。例如，触控大屏主题不能因为资源加载成功就被启用到单色 `240x320` 设备。

## 当前目录的实施校验

正式实现前应完成以下自动化校验，防止文档和代码漂移：

1. 从应用目录和 `ScreenRegistry` 导出全部顶层稳定 ID，与本表对比。
2. 每个 `route_id` 有一个固件 `CapabilityDescriptor`，并声明 `required_slots`、动作参数类型和危险级别。
3. 每个已启用 UX Pack 都能导出自己的可用能力清单。
4. 每个主题构建都对目标 UX Pack 验证必需槽位、焦点顺序、profile 规定的触控面积要求和返回路径。
5. 新增用户可见能力时，代码评审必须同时更新契约、主题 SDK 版本判断和本目录。

在契约尚未冻结前，主题 API 必须标记为预览版；第三方发布包不应被承诺跨固件版本永久兼容。
