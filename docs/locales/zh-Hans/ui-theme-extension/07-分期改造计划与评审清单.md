# 07：实施依赖序列与完整性评审清单

## 这份计划解决什么问题

本计划不是把主题能力拆成若干个对用户可见、范围递减的版本，也不是挑少数页面先声明“已经支持主题”。它规定的是实现时的**工程依赖顺序**：先冻结所有 ESP32 目标的能力与呈现契约，再建立 FFat 默认主题和受限渲染器，之后接通 SD 包管理与第三方工具。任何外部主题下载入口、主题启用入口或第三方 SDK 的发布，都以全部 ESP32 呈现面通过验收为前提。

本方案覆盖的设备和构建路径是：Tab5、T-Display P4 TFT、T-Display P4 AMOLED、T-LoRa Pager（SX1262 与 LR1121 变体）、T-Deck、T-Watch S3，以及 T-Deck Pro（A7682E 与 PCM512A 变体）。它们的当前编译与产品绑定依据见 [13：当前 UI 源码盘点与解耦改造地图](./13-当前UI源码盘点与解耦改造地图.md)。Linux 模拟器、Linux uconsole、Cardputer 和 nRF52 不在本次授权的改造范围中；它们既不参与本计划的实现承诺，也不应被当作 ESP32 主题功能的验收替身。

所有阶段都要保持 `builtin.default` 的完整默认 UI 位于 FFat、第三方主题只位于 SD、主题文件不能执行代码、能力与路由由固件决定这四项不变量。阶段之间可以分开合并代码和验证证据，但不能以省略某一类屏幕/页面为发布条件。

```text
0. 冻结 ESP32 目标矩阵、能力目录与资源预算
1. 冻结稳定契约并导出全量机器可读目录
2. 建立 FFat factory theme、受限 renderer 与恢复呈现
3. 迁移全部 shell、页面、overlay、手表与 mono 呈现面
4. 接入 SD 主题安装、激活、回退和 Extensions 交互
5. 完成主机打包工具、SDK、CI 和全目标自动化验收
6. 完成实机故障注入、性能、可访问性与发布治理
7. 开放经过签名/审核的第三方主题分发
```

## 阶段 0：冻结 ESP32 目标矩阵、存储模型和资源预算

**目标**：为每个实际 ESP32 构建目标指定一个可验证的主题 profile，而不是用一个触控设备的结果代表其他设备。

| ESP32 目标 | 当前构建/呈现路径 | 必须冻结的主题 profile 内容 | 当前需要补齐的配置事实 |
| --- | --- | --- | --- |
| Tab5 | ESP-IDF、`apps/esp32_lvgl`、兼容 UX Pack | 分辨率、方向、触控、色深、PSRAM、FFat/SD 预算、全部 route 集合 | `target_build_binding`、`target_ux_binding` 与运行时 profile 输出一致。 |
| T-Display P4 TFT | ESP-IDF、P4 触控 UX Pack | TFT 尺寸/方向、触控、色彩、地图/图表缓存、输入法、全部 route 集合 | 保留已存在的 P4 target ID，并导出完整 CapabilityDescriptor。 |
| T-Display P4 AMOLED | ESP-IDF、P4 触控 UX Pack | AMOLED 色彩/刷新限制、烧屏策略、资源色深、触控、全部 route 集合 | 将面板差异显式写入 profile，不让主题自行猜测。 |
| T-LoRa Pager SX1262 / LR1121 | ESP-IDF/PlatformIO、兼容 UX Pack | 紧凑显示、按键/焦点、低内存、字体、状态栏、全部 route 集合 | 补齐 IDF 启动运行时的 target/profile 解析，不能回退为泛化 `esp_idf` 字符串。 |
| T-Deck | ESP-IDF/PlatformIO、兼容 UX Pack | 横屏、键盘/编码器或触控输入、焦点、长文本、全部 route 集合 | 固定运行时 `ux_pack_id` 与输入能力来源。 |
| T-Watch S3 | ESP-IDF/PlatformIO、兼容 UX Pack + watch/chat-watch | 表盘、通知、睡眠/唤醒、窄屏触控、手表专用聊天呈现、全部 route 集合 | 将 `watch_face.cpp` 与 `chat_watch/` 纳入同一契约和 FFat 默认资源构建。 |
| T-Deck Pro A7682E / PCM512A | PlatformIO、`screen_240x320` mono 路径及蜂窝分支 | 240×320 单色/低资源布局、键盘焦点、蜂窝电话/SMS/邮件/设置页、全部 route 集合 | 在 product composition、runtime config 与 `ux_pack_id` 映射中补齐 target ID、profile 和包绑定。 |

还必须冻结以下设备无关的数值与策略，并把它们写入 target profile、SDK 和 CI fixture：

- FFat 分区容量、默认主题镜像预算、`TMFH` 头部版本和 App/FFat 成对更新策略；
- SD 卡文件系统类型、长文件名/大小写规则、移除卡时的资源句柄失效语义、目录容量和保留空间；
- 各 profile 的布局节点数、树深度、文本长度、图像像素量、字体页、缓存块、流读取块和任务栈占用预算；
- 每一种输入方式的焦点顺序、物理按键映射、触控命中区要求、Back、取消、确认和危险动作确认规则；
- 主题签名、官方目录签名、侧载开关、物理确认、撤销和过期策略；
- 需要实机验证的板卡、面板、SD 卡、PSRAM 和蜂窝外设组合。

**退出条件**：上述目标表的每一行都有冻结的 ID、profile、UX Pack、能力导出文件、预算文件和验收设备；不存在“generic ESP32”或由某个大屏 target 默默代替其他 ESP32 target 的配置。

## 阶段 1：全量能力契约与机器可读目录

**目标**：让所有当前 UI 在开始替换视觉之前，先拥有稳定、可测试的语义描述。

- 为每个 `capability_id`、`route_id`、`action_id`、`slot_id`、`token_id` 建立带版本的描述符，并列出状态、错误、权限、确认和数据脱敏规则。
- 从 `app_catalog_builder.cpp`、各 UX Pack、`screen_240x320`、手表页面、板级启动和全局 overlay 导出完整目录；条件编译的页面也必须以 target/profile 条件记录。
- 对每条 route 记录进入参数、返回目标、必需/可选 slot、焦点图、输入方式、危险动作、空/加载/错误/离线状态和内建专用 widget。
- 将地图、GNSS 图、IME、密码输入、设置编辑器、呼叫/配对提示等专用能力登记为固件 widget；主题只能决定被契约允许的外层容器、令牌和资源，不能替换算法或安全语义。
- 为所有 target 的默认 UI 生成契约覆盖测试：无外部主题时，功能、可达性、返回行为和安全确认必须与基线一致。

**涉及区域**：应用目录构建、`AppScreen`/`CallbackAppScreen`、菜单运行时、各屏幕 shell/runtime/components、`ScreenRegistry`、UX Pack、`screen_240x320` dispatcher、手表呈现和启动 shell。具体文件见 [13](./13-当前UI源码盘点与解耦改造地图.md) 第 4 至第 8 节。

**退出条件**：每一个阶段 0 中的 target 均能导出其能力、路由、slot、动作、输入和可达性清单；目录不含靠图标指针或 LVGL 回调才能解释的隐式语义。

## 阶段 2：FFat factory theme、受限渲染器和恢复呈现

**目标**：使默认 UI 本身也遵循主题运行时边界，且 FFat 故障时设备仍可诊断和恢复。

- 实现 `FactoryThemeImageBuilder`，为每个 ESP32 profile 输出 FFat 中的 `builtin.default`；该镜像含 `package.ini`、`theme.ini`、`theme.tmb`、`assets.index`、图标、字体和 `FactoryThemeHeader` 所覆盖的哈希。
- 实现有界的 INI 行读取器、二进制索引读取器、`theme.tmb` 读取器和资源流读取器。设备侧不得为主题构建 JSON 对象树、`cJSON` DOM、`std::vector` 文件清单或无界字符串。
- 实现 `ThemeLayoutValidator`、`ThemeTokenResolver`、`ThemeAssetReader`、`ThemeRenderer`、固件 widget registry 和统一的焦点/Back/确认协调器。
- 实现独立 `rescue` 恢复呈现：固定诊断码、FFat/SD 挂载状态、当前 target/profile、恢复指引、重启与允许的维护入口。它不读取 FFat 或 SD，也不包含第二份完整正常 UI。
- 实现 Factory/SD provider 的句柄所有权、缓存、文件关闭、SD 热拔插、解码失败和帧边界切换协议。

**退出条件**：每个目标均能从其 FFat `builtin.default` 启动并通过 header/哈希/契约校验；任何 FFat 不可用、FFat 头不匹配或关键默认资源不可读的组合均进入带完整诊断信息的 `rescue` 恢复呈现。

## 阶段 3：迁移全部 ESP32 呈现面

**目标**：清除普通 UI 路径对编译进应用的颜色、图标、字体和硬编码布局的依赖。

迁移单位不是“挑几个高频页面”，而是下表中每一类完整集合。每一个集合都要同时迁移正常、空、加载、错误、离线、危险确认和返回路径。

| 呈现集合 | 必须覆盖的内容 | 迁移完成判据 |
| --- | --- | --- |
| 启动与 shell | boot、splash、AppCatalog、菜单、仪表盘、顶栏、时间/电池/链路状态、屏保、反馈、busy、toast、modal、系统/配对/来电提示 | 不再由普通路径直接读取 `ui_theme.h`、`images.h` 或 C++ icon descriptor。 |
| 触控大屏应用 | chat、map/GPS、sky plot、contacts、team、tracker、energy sweep、calculator、SSTV、USB、settings、network、extensions、walkie-talkie、shutdown，以及 feature flag 产生的应用 | 所有 `AppCatalog` 条目和子 route 都由 CapabilityView + renderer 生成。 |
| 专用触控页面 | 地图 viewport、路线/海拔图、GNSS 图表、聊天会话/编辑器、节点信息、设置编辑器、Wi-Fi/固件更新、网络详情 | 算法/业务留在固件，视觉容器和资源经 theme contract 提供。 |
| 240×320 与蜂窝页面 | Map、SkyPlot、Network、Settings、Tracker、Walkie、SSTV、USB、Chat、Team、Contacts、Extensions、ProtocolProbe、Cellular、Phone/SMS/Email/Radio/Mail settings | `PageKind` dispatcher、黑白行/按钮布局、焦点和键盘输入均走该 profile 的二进制模板。 |
| 手表页面 | watch face、chat-watch、通知、唤醒/屏保、紧凑顶栏与所有手表可达 route | 手表特有 slot 与资源被 FFat 默认主题和外部主题 profile 完整声明。 |
| 输入与安全呈现 | 键盘、编码器、触控、IME、秘密输入、确认/取消、破坏性操作与回退入口 | 主题不得删改 required action 的可达性或调换确认语义。 |

**退出条件**：所有 ESP32 target/profile 上的完整目录均可由 `builtin.default` 呈现；静态分析与运行时测试证明普通 UI 路径不再绕过 Theme Provider 直接消费旧颜色、图片、字体或布局代码。为兼容已有业务入口而存在的适配层必须具备删除计划和调用计数，不得成为永久双轨渲染。

## 阶段 4：SD 主题、安装事务和 Extensions 交互

**目标**：在完整默认呈现已稳定后，把外部主题安全地纳入用户的扩展生命周期。

- `.tmt` 仅作为 ZIP 分发容器；安装后的 payload 始终解压至 `/trailmate/packs/themes/<theme-id>/versions/<version>-<sha8>/`，并由二进制双槽 `theme-index`、`theme-state` 管理。
- `Extensions` 的主题分组覆盖发现、兼容性解释、签名状态、下载、侧载、安装、校验、预览、激活、恢复 `builtin.default`、更新、卸载、诊断和撤销状态。
- 下载/解压/校验/提交与激活保持不同事务；安装完成默认不改变活动主题；每个事务记录 generation、CRC、哈希、错误码和可恢复状态。
- 启用前对**该 target/profile 的全部需要呈现的 route**执行布局、slot、动作可达性、资源和预算预检；不能以少量示例 route 代表整套主题可用。
- SD 缺失、只读、容量不足、下载中断、解压失败、索引双槽损坏、资源读取失败、卡热拔插和激活中掉电均要有固定的状态迁移和可解释 UI。

**退出条件**：每种 ESP32 target/profile 都能完成“下载或侧载 → 校验 → 安装 → 预览 → 启用 → 重启保持 → 恢复 FFat 默认 → 卸载”的全流程；所有失败路径保持原活动主题、FFat 默认主题或 `rescue` 之一，没有半安装或半激活状态暴露给用户。

## 阶段 5：主机工具、SDK 与自动化验收

**目标**：使主题作者在设备外得到与固件相同的确定性结论。

- 实现 `init`、`validate`、`build`、`inspect`、`test`、`sign`、`verify`、`factory-image` 和 `contract-export` 命令；每条命令的输入、输出、退出码、诊断格式和确定性要求以 [06：主题包工具链规范](./06-主题包工具链规范.md) 为准。
- SDK 发布所有 ESP32 target/profile 的能力目录、slot 字典、动作目录、资源键、布局 schema、预算、样例、测试向量和迁移说明。
- 工具链对每个 target/profile 构建 `.tmt` 和 FFat 默认主题镜像；主题若只声明部分 profile，工具必须明确输出不兼容 profile，不得伪装成通用包。
- CI 对每个主题执行路径穿越、重复条目、ZIP bomb、签名失败、版本失配、资源超限、坏哈希、未知节点、焦点不可达、危险动作不可达、长文本、RTL、无数据、离线和错误状态测试。
- 主机验证器和固件验证器共享 fixture；相同坏包必须得到相同拒绝类别与错误码。

**退出条件**：不连接设备即可重现构建、校验和错误诊断；所有 ESP32 profile 的完整 route 集合都有可追溯的构建产物和测试报告。

## 阶段 6：实机验证、故障注入和发布门槛

**目标**：证明设计在真实 ESP32 的内存、存储、输入和掉电条件下成立。

- 对阶段 0 的每个 target/变体使用真实板卡执行冷启动、主题切换、全 route 遍历、地图/GNSS、聊天编辑、设置确认、扩展安装、蜂窝页面（适用时）、手表页面（适用时）和键盘/编码器操作。
- 测量启动时间、首屏时间、页面切换时延、峰值 RAM、任务栈余量、PSRAM、FFat/SD 占用、资源句柄数量和长期反复切换后的回收情况。
- 注入无 SD、SD 热拔插、SD 写满、下载中断、解压中断、双槽损坏、签名/哈希错误、FFat 不挂载、`TMFH` 失配、App/FFat 配对更新中断等故障。
- 完成人工可访问性审查：户外可读性、夜间对比、色觉差异、字体回退、触控命中区、键盘焦点、屏幕阅读文本替代（若硬件支持）和误触风险。
- 发布前归档每个 target/profile 的性能报告、故障报告、截图/视频、串口诊断和主题兼容矩阵。

**退出条件**：所有 ESP32 target/变体都满足冻结的预算、恢复、可达性和完整 route 验收；不存在依赖开发板偶然配置、未验证屏幕或未覆盖 feature flag 的发布例外。

## 阶段 7：第三方开放与长期治理

**目标**：在接口、验证、恢复和审核均已具备证据后，向第三方开放主题制作和分发。

- 发布版本化 Theme SDK、中文开发指南、包格式、二进制布局协议、错误码、样例、目标矩阵、兼容规则、签名说明和撤销机制。
- 建立开发者身份/公钥登记、目录签名、包审核、版权与商标处理、恶意视觉欺骗处理、撤销、过期和申诉流程。
- 对目录包执行自动格式校验、完整 route 回归、交互审查、资源安全扫描和适用 target/profile 的实机抽检。
- 建立主题 API 弃用窗口、兼容层、设备固件版本矩阵、SDK 版本矩阵和问题主题的远程撤销目录。
- 主题不拥有业务数据、网络权限、文件权限、进程权限或执行入口；开放治理不能改变该安全边界。

**退出条件**：第三方可独立构建、签名、验证和提交覆盖其声明 profile 的主题；审核系统可以追溯包来源、兼容性、测试证据和撤销状态，设备可安全回退。

## 完整交付范围检查表

在允许用户从 Extensions 下载、安装或启用外部主题之前，评审者必须逐项确认：

- [ ] FFat 的 `builtin.default` 已为所有 ESP32 target/profile 生成、签名、烧录并通过 `TMFH` 校验；正常应用固件中不存在第二份完整默认 UI 资源。
- [ ] SD 安装目录、`.tmt` 分发归档、二进制安装索引、活动状态双槽和掉电恢复行为符合 [03](./03-主题包格式与固件接口.md)、[04](./04-扩展中心与安装生命周期.md)、[08](./08-内置默认主题与SD加载协议.md)。
- [ ] Tab5、两种 P4、Pager 两种无线变体、T-Deck、T-Watch 和 T-Deck Pro 两种硬件变体均有明确的 profile、能力目录、默认主题资源和实机证据。
- [ ] 启动、菜单、仪表盘、顶栏、屏保、表盘、所有 overlay、所有 AppCatalog/`PageKind` 页面、条件编译页面、蜂窝页面、输入与恢复路径均纳入主题契约和默认主题验收。
- [ ] 每一项业务能力仍由固件路由与 action dispatcher 执行；主题只能选择已授权的布局、资源与令牌。
- [ ] 设备侧主题读取路径没有 JSON DOM、`cJSON`、无界容器、递归不受控解析或大型自动局部对象。
- [ ] `rescue` 恢复呈现包含固定诊断与维护能力，且不依赖 FFat、SD 或外部主题。
- [ ] Extensions 完整提供发现、解释、下载、侧载、安装、校验、预览、启用、恢复默认、更新、卸载、诊断和撤销状态。
- [ ] 打包工具与固件验证器对所有 profile、所有 route 和全部负面 fixture 给出一致的结果。
- [ ] Linux、nRF52 及其他非 ESP32 平台没有被纳入本设计的代码、测试或交付承诺。

## 风险清单与控制措施

| 风险 | 后果 | 设计控制 |
| --- | --- | --- |
| 主题可执行代码 | 远程代码执行、设备不稳定、权限绕过 | 声明式二进制格式、ZIP 白名单、无脚本/无动态链接、固件 widget registry。 |
| 主题漏掉必要动作 | 用户无法发送、返回、取消或确认 | 必需 slot、动作图、焦点图和 route 全量可达性校验；失败拒绝启用。 |
| 设备差异被主题覆盖 | 小屏、手表、键盘或蜂窝路径出现错误入口 | UX Pack 与 target profile 先计算能力集合；主题 manifest 仅声明兼容性。 |
| 图像/解压资源过大 | 内存耗尽、卡死、栈溢出 | 主机预检、固件上限、有界流读取、持久/成员存储和实机峰值测量。 |
| 目录或包被篡改 | 恶意视觉欺骗或损坏安装 | HTTPS、目录签名、归档 SHA-256、受保护发布 CI 签名、撤销机制和本地物理确认。 |
| 更新中断 | 当前主题损坏、设备无法操作 | staging、原子提交、双槽索引、活动主题回退、FFat 默认和独立恢复呈现。 |
| 文档与接口漂移 | 第三方主题大量失效 | 从契约导出 SDK、版本化目录、固件/工具共享 fixture、全 profile CI。 |
| 主题泄露敏感状态 | 凭据或业务数据外泄 | 严格脱敏的 `CapabilityView`；主题不访问服务、存储、网络或密钥。 |

## 实施过程中的强制工程检查

以下要求属于实际编码阶段；本轮只记录设计，不修改固件：

1. 每次修改函数、类或方法前，对目标符号执行 GitNexus 上游影响分析，并向评审者报告直接调用者、受影响流程和风险等级。
2. 影响分析为 `HIGH` 或 `CRITICAL` 时，先记录影响与缓解措施，再决定拆分方式和测试范围。
3. 修改 ESP 包安装、UI 运行时、配置保存、BLE/Meshtastic 路径或 Android BLE 路径时，执行仓库规定的栈卫生检查；主题解析没有例外。
4. 包安装改动必须覆盖断电、下载失败、哈希失败、无存储空间、路径穿越、版本回退和活动主题卸载。
5. 准备提交前使用 GitNexus `detect_changes()` 复核实际变更只涉及预期符号和执行流。

## 评审必须给出的冻结结论

开始任何固件代码改造前，评审记录必须明确回答，而不是留给实现人员现场选择：

1. 每个 ESP32 target/硬件变体的正式 target ID、UX Pack、layout profile、显示与输入参数是什么？T-Deck Pro 缺失的 composition/runtime binding 由哪个变更补齐？
2. 每个 profile 的 FFat、SD、RAM、PSRAM、任务栈、图像、字体、节点树和缓存预算是多少，如何在 CI 和实机上量测？
3. 是否允许侧载；若允许，开发者模式、物理确认、签名要求、错误呈现和撤销如何工作？
4. `builtin.default` 的 App/FFat 成对升级采用哪一种已实现的分区和掉电回滚方案？
5. 各 route 的必需 slot、动作、焦点、输入、危险确认、脱敏数据和专用 widget 由谁维护，契约何时弃用？
6. 谁负责第三方开发者公钥、目录审核、商标/版权投诉、撤销与安全通告？

这些结论应进入正式 ADR，并与本目录的协议文件和自动化 fixture 一同受版本控制。只有这些结论、完整实现和完整验证证据同时具备，外部主题分发才可以对用户开放。
