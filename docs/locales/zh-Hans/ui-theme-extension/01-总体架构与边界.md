# 01：总体架构与边界

## 结论

Trail Mate 应采用“**业务与能力在固件，呈现在主题包**”的分离方式，而不应把完整页面代码、导航或业务逻辑下放给扩展包。主题能重排一个页面中的受控组件、替换图标和视觉风格；它不能影响任何固件能力是否存在、动作如何执行、哪些数据可见，或用户是否能到达某条路由。

这项选择适合嵌入式设备：它避免动态执行第三方代码，保持 ESP32 的 RAM、任务栈、权限和故障域可控，同时仍让第三方具备足够的视觉创作空间。

## 适用范围：只覆盖 ESP32 固件，且必须完整覆盖

本方案的实施范围被严格限定为 **Trail Mate 的 ESP32 固件构建、启动、存储和 LVGL 呈现路径**。它不要求、也不授权改造 Linux 模拟器/GTK、Linux uConsole/Cardputer shell、nRF52 节点或它们的构建入口。共享目录中的代码如果同时被其他平台编译，只能以不改变其行为的方式为 ESP32 增加适配边界；Linux/nRF52 不是本主题系统的兼容目标、验收目标或主题包目标。

“完整覆盖”在这里有精确含义：所有当前 ESP32 目标的出厂 UI 都必须拥有与各自固件 ABI 配对的 FFat `builtin.default`，且所有用户可见页面、嵌入页、启动/菜单/屏保/表盘、覆盖层、输入/确认和错误呈现都必须进入能力契约与默认主题资源清单。**不能**以“先做一个 UX Pack”“只做几个关键路由”“其余页面继续硬编码”为交付范围。

这不要求每一份第三方主题包同时支持所有屏幕。第三方主题可以在清单中声明它支持的 ESP32 target/profile；固件必须只在匹配目标上允许安装和启用。完整性要求约束的是固件架构和官方 `builtin.default`，不是强迫所有主题作者为每种硬件画同一套布局。

当前 ESP32 覆盖清单、源码入口和目标构建状态以 [13：当前 UI 源码盘点与解耦改造地图](./13-当前UI源码盘点与解耦改造地图.md) 为准；那里还记录了 T-Deck Pro 目前缺少 product-composition target binding 这一必须先补齐的配置缺口。

## 现状依据

当前代码已经形成了适合作为改造起点的三个边界。

## 目标与非目标

### 目标

- 保留当前全部界面资源、现有页面布局和交互作为 `builtin.default` 出厂默认主题；主题资源和布局写入 FFat 出厂镜像，固件只编译能力、路由、动作和加载器。它是产品基线，而不是临时兼容层。
- 用户能在 `Extensions` 中浏览、下载、安装、预览、启用、更新和卸载主题包。
- 已启用主题能替换图标、颜色、字体规格、间距、圆角、背景和页面内组件布局。
- 同一个主题可声明支持哪些设备 UX Profile、屏幕尺寸与输入形态。
- 第三方可依据公开、版本化的接口文档和工具构建主题包。
- 固件始终拥有能力、权限、数据加载、业务规则、动作执行、导航安全与可访问性责任。
- 不兼容、损坏、资源超限或运行时失败的主题不会阻止设备进入可用界面。

### 明确非目标

- 不允许主题包携带或执行 C/C++、ELF、动态库、Lua、JavaScript、WASM、字节码或安装脚本。
- 不允许主题注册新的无线协议、后台任务、网络访问、文件系统访问、设置项或硬件驱动。
- 不允许主题增加、删除、禁用、重命名、重排序为不可到达的业务能力或动作。
- 不允许主题直接读取聊天正文、密钥、Wi-Fi 凭据、GPS 原始流、文件路径或其他业务存储。
- 不把设备差异、板级引脚、SDK/HAL、构建入口或协议解释放入主题包。
- 不允许用户把当前默认主题移动到 SD、覆盖、替换或删除 `builtin.default`；它属于受固件验证的 FFat 出厂资源。
- 主题系统不开放“第三方业务插件”或“第三方自定义页面”。这类需求属于另一套受权限、沙箱和审核约束的应用扩展架构，不属于本方案的主题接口。

## 分层模型

```text
┌─────────────────────────────────────────────────────────────────┐
│  固件业务层：聊天、地图、团队、设置、扩展、无线、存储、权限       │
│  只暴露快照（状态）和动作端口（意图）；不认识主题资源              │
└─────────────────────────────┬───────────────────────────────────┘
                              │ Capability Contract
┌─────────────────────────────▼───────────────────────────────────┐
│  固件界面壳：路由、焦点、返回栈、动作分发、可访问性、降级与回退    │
│  生成固定的 capability_id / route_id / action_id / slot_id        │
└───────────────┬───────────────────────────────────┬─────────────┘
                │                                   │
┌───────────────▼───────────────┐   ┌───────────────▼────────────┐
│ 编译期 UX Pack                 │   │ 动态 Theme Bundle           │
│ 设备选择：页面集合、功能深度、 │   │ 主题选择：图标、令牌、       │
│ 输入映射、可用路由             │   │ 受约束的布局和装饰           │
└───────────────┬───────────────┘   └───────────────┬────────────┘
                └───────────────┬───────────────────┘
                                ▼
                    ESP32 上的 LVGL 渲染后端
```

运行时的选择顺序必须固定如下：

```text
目标/板级能力
  → 选择内置 UX Pack
  → 计算该设备可用能力与路由集合
  → 选择已验证的主题或内置回退主题
  → 固件壳以能力契约构建页面语义树
  → 主题仅为语义树提供令牌、资源与布局
  → 渲染器绘制并把输入映射回固件动作
```

关键点是：主题的输入永远是“已被固件允许的语义树”，而不是主题自建的页面或导航图。

## 当前界面作为内置默认主题

`builtin.default` 是本方案的起点和兜底，而不是要额外设计一套新 UI。它等价于当前用户看到的图标资源、`ui_theme` 设计值、菜单与页面布局以及各页面交互行为。实施时，现有编译期图片与视觉/布局常量要逐步转换为出厂主题负载，写入 FFat；用户在没有安装任何扩展时看到的界面、可用能力和操作行为必须保持不变。

```text
固件镜像
├── 能力契约、路由、动作、渲染器、Theme Runtime
└── 独立 rescue 恢复呈现（固定诊断、恢复指引、重启与受控维护入口）

FFat 出厂分区
└── builtin.default
    ├── 当前默认图标/颜色/视觉令牌/页面布局二进制
    ├── FactoryThemeHeader 与资源索引
    └── 与固件能力契约匹配的版本与哈希

SD 卡
└── 用户安装主题
    └── 在 builtin.default 的能力壳上覆盖令牌、资源和布局
```

因此，外部主题不是“替代固件前端”，而是对 FFat 中 `builtin.default` 的受约束覆盖层。一个外部主题未提供的资源使用 FFat 出厂资源；一个页面未提供有效布局使用 FFat 默认布局；主题整体不能加载时，整个设备回到 `builtin.default`。只有 FFat 也不可用时才进入固件 `rescue`。

`builtin.default` 必须具有下列不可变属性：

- 随出厂 FFat 镜像发布，所有支持 UI 的目标都有一份与固件契约相适配的默认资源变体；
- 不出现在可卸载扩展列表中，不写入 `theme-index.a/b`，也不能被同名 SD 目录覆盖；
- 不需要 SD 卡、远程目录、下载器或第三方签名才可使用，但启动前必须挂载和验证 FFat FactoryThemeHeader；
- FFat 不可挂载、默认主题损坏或契约不匹配时，明确进入固件内 `rescue`，而不是假装仍能加载完整默认主题。
- 是首次启动、恢复出厂后以及外部主题故障时的唯一必定可用呈现；
- 提供所有能力契约的完整基线，从而可作为主题 SDK 和自动化回归的参考实现。

## 两类包的职责界线

| 维度 | 编译期 UX Pack | 动态 Theme Bundle |
| --- | --- | --- |
| 由谁提供 | Trail Mate 固件 | Trail Mate 或第三方作者 |
| 何时选择 | 启动/目标组合时 | 安装后由用户启用，可在安全点切换 |
| 决定什么 | 页面集合、功能深度、输入绑定、设备产品体验 | 图标、色彩、字体规格、间距、控件形态和组件布局 |
| 是否能隐藏功能 | 可，因为这是产品/设备能力决定 | 不可 |
| 是否能决定路由 | 可声明该设备可用路由 | 不可，只能布局已经存在的路由 |
| 是否包含代码 | 固件 C++ | 不含可执行代码，只含受验证的数据资源 |
| 是否访问业务服务 | 通过固件编译边界 | 不允许 |

例如，某个 ESP32 target/profile 的固件能力目录没有完整聊天工作流时，主题不能把“聊天”变出来；`deck_full` 已导出完整聊天工作流时，主题则不能把发送、返回、会话选择等必要能力拿掉。

## 能力契约：前后端分离的核心

建议把“前端”定义为主题渲染层，把“后端”定义为固件能力和呈现模型层，并在两者之间建立版本化契约。

每个界面状态由固件构造一个 `CapabilityView`，至少包含：

- `capability_id`：稳定业务能力，例如 `chat.conversation`；
- `route_id`：当前页面/子页面，例如 `chat.compose`；
- `state`：只读、已脱敏的显示快照；
- `required_slots`：当前路由必须呈现的语义槽位；
- `optional_slots`：可因屏幕密度折叠的辅助信息；
- `actions`：允许触发的固定 `action_id`、参数类型、是否危险、是否需要确认；
- `availability`：由固件计算的可用/不可用/加载中/错误状态与原因码；
- `accessibility`：目标 profile 规定的命中区要求、文本替代、焦点顺序和危险动作确认要求。

主题解析器只能做三件事：为槽位选择资源、把槽位排入允许的容器、为令牌给出值。所有 `action_id` 由固件绑定；主题文件中不能出现回调、表达式、URL、文件路径、脚本或条件执行逻辑。

## 如何保证“布局可变，但能力不变”

仅用“主题作者承诺不隐藏按钮”并不可靠，必须由运行时结构性保证。

1. 固件为每条路由给出[**必需槽位清单**](./02-界面能力目录与稳定契约.md#required-slot-catalog)。例如 [`chat.compose` 的确切清单](./02-界面能力目录与稳定契约.md#chat-compose-required-slots) 包含标题、编辑器、发送、取消和投递状态槽位；设备生成的 `slots.json`/二进制契约会在 target/profile 过滤后给出该次会话的精确集合。
2. 主题布局使用槽位 ID，不使用任意业务函数名。一个必需槽位只能被放置、折叠到受支持的溢出容器，或采用固件预定义的紧凑呈现；不能删除。
3. 校验器验证每个必需槽位恰好可达一次，并验证每个必需动作具有可见名称/图标/焦点入口；危险动作还要保留确认语义。
4. 固件始终拥有全局 `Back`、焦点恢复、异常退出和安全模式手势；主题不能拦截或重定义它们。
5. 当主题遗漏某个可选资源时使用内置资源；遗漏必需槽位、类型不匹配、超出预算或渲染失败时，整页回退内置布局，不能半残缺地继续。
6. 自动化合约测试从能力目录生成“每个路由的槽位可达性、动作可达性、焦点可达性”断言。主题 CI 与固件 CI 都必须运行它。

这样，主题可以把“发送”从底部右侧改为顶栏图标、把菜单从网格改成列表、把状态卡改成徽章，但不能令发送、设置保存、确认删除或返回上级变得不可达。

## 主题可覆盖的范围

本方案将主题覆盖严格限定为以下三类可验证能力，避免把 LVGL 的全部对象图暴露成不稳定 API。

| 覆盖层 | 主题可做的事 | 主题不可做的事 |
| --- | --- | --- |
| 资源映射 | 为稳定 `asset_id` 提供图标、插图、九宫格背景和可选字体资源 | 引用任意固件内存地址，改变业务图片数据，加载网络图片 |
| 设计令牌 | 覆盖颜色、字号档、线宽、圆角、间距、阴影、透明度、动效档位 | 改变固件状态机、字号可读性下限、危险状态颜色语义 |
| 布局模板 | 在页面声明的容器中排列 `slot_id`，选择网格/列表/栈/标签页等受支持布局 | 新建业务路由、删除必需槽位、绑定自定义事件或调用服务 |

地图瓦片、聊天消息、二维码、头像、定位覆盖物等业务数据由固件继续拥有；主题只可定义它们的承载容器、边框、图例样式和状态图标。

## 固件侧完整新增与重构模块

下表是覆盖全部 ESP32 页面所需的**完整**模块边界，不是只为演示路径设置的集合。现有文件如何迁移到这些边界见 [13：当前 UI 源码盘点与解耦改造地图](./13-当前UI源码盘点与解耦改造地图.md) 第 10 节。不能让未迁移页面继续绕过这些模块直接读取 `ui_theme.h`、C 图标或旧的 AppScreen 图标指针。

| 模块 | 完整责任 | 必须覆盖的现有区域 |
| --- | --- | --- |
| `CapabilityRegistry` 与 `CapabilityContract` | 汇总 ESP32 target/profile、编译期 UX Pack、FeatureFlags 和硬件状态；导出全部 capability/route/action/slot、危险级别、可访问性和契约哈希。 | AppCatalog、UX Pack、所有顶层/嵌入页面、全局 shell。 |
| `PagePresenter` 家族 | 每个页面把业务状态转换为有界、脱敏 ViewModel，并将固定 action 交给固件 dispatcher。 | Dashboard、Chat、Contacts、Team、Map/GNSS、Tracker、Calculator、SSTV、USB、Settings、Network、Extensions、Walkie、Protocol Probe、Cellular、Shutdown、C6 Companion。 |
| `ThemeProvider` 家族 | `FactoryThemeProvider` 从 FFat 固定根验证并读取 `builtin.default`；`SdThemeProvider` 从 SD 双槽索引读取外部主题；统一资源句柄和 generation 语义。 | 每个 ESP32 target 的默认主题与可安装外部主题。 |
| `ThemeIndex/State/Transaction` | 用固定大小双槽索引、活动状态、staging 和可恢复事务管理安装、更新、启用、回滚和 SD 热拔插。 | Extensions、主题目录、所有外部主题生命周期。 |
| `ThemeCatalogClient` 与 `ThemePackageVerifier` | 处理 TMCP 分页目录、受限 `.tmt`、签名、哈希、路径、资源预算和兼容性；不使用 JSON 大对象树。 | Extensions 下载/侧载路径。 |
| `ThemeBinaryReader` 与 `ThemeLayoutValidator` | 有界读取 `theme.ini`、`theme.tmb`、`assets.index` 和资源流；按全部契约校验节点、slot、action、target/profile、字体和预算。 | 每一条可主题化 ESP32 route。 |
| `ThemeRenderer` 与内建 `WidgetRegistry` | 将已验证布局和 ViewModel 生成 LVGL 树；统一 token、字体、asset、焦点、Back、错误/危险语义；专用地图/GNSS/IME/设置编辑器以固件 widget 注册。 | 所有大屏、键盘、单色、手表投影及跨页 overlay。 |
| `Shell/Overlay/Rescue Presenter` | 覆盖启动、菜单、仪表盘、状态栏、屏保、表盘、通知、进度、弹窗、IME、配对/来电/系统提示；`rescue` 提供固定诊断、恢复指引、重启和受控维护入口，且不依赖 FFat。 | 不属于顶层 AppCatalog 的全部用户可见面。 |
| `Esp32TargetThemeProfile` | 为 Tab5、P4 TFT/AMOLED、T-LoRa Pager、T-Deck、T-Watch、T-Deck Pro 等 ESP32 目标统一输出显示、输入、色深、FFat/SD/PSRAM 和布局档；修复当前 target binding 与启动运行时不一致。 | IDF 与 Arduino/PlatformIO 两条 ESP32 启动路径。 |
| `FactoryThemeImageBuilder` 与 `theme_pack.py` | 从当前默认视觉源码/资源构建每个 ESP32 target 的 FFat 镜像；为第三方编译、验证、签名、inspect 和所有路由验收。 | 出厂烧录、OTA 配对、CI 和第三方 SDK。 |
| `Esp32ThemeTestHarness` | 在真实 ESP32 target 上验证全部 route、资源错误、SD 拔出、FFat 错误、回退、焦点/键盘/触控和危险确认。 | 全部 ESP32 目标；Linux/nRF52 不作为替代验证环境。 |

页面业务模块应从“直接写死颜色/图标/几何并操作 LVGL”迁移为“声明能力槽位、提供 ViewModel 与动作”。这与现有 Presentation Model 分层方向一致，但要求覆盖所有 ESP32 页面，而非只迁移少数示例页。

## 嵌入式安全与资源原则

- 主题包不得在 UI 任务栈上创建大型解压、图像或布局对象；下载、解压和验证在受控后台流程完成，渲染只使用已经验证的小型索引和流式资源。
- 不允许 ZIP 路径穿越、绝对路径、符号链接、嵌套归档、重复解压或未声明资源。
- 所有尺寸、文件数、像素数、解压后总量、单资源大小、布局节点数、文本长度和字符串表数量都有按内存档位定义的硬上限。
- 所有资源都要有 SHA-256；公开设备目录中的包还应具有受保护发布 CI 生成的发布签名和目录签名。SHA-256 解决完整性，不单独构成发布者身份验证；第三方作者的身份、PR 与源提交由发布清单保留。
- 主题激活只能在 LVGL 帧边界或页面切换安全点发生。激活前保留旧主题，激活失败立即回滚，不让 UI 进入无主题状态。
- 每个主题的加载、验证、激活、回退和崩溃恢复都记录简短诊断码，但不得在日志写入敏感业务数据。

## 兼容与降级原则

主题兼容性必须同时满足：`theme_api` 版本、固件最低版本、目标 UX Profile、显示/色深约束、输入方式、内存档位和能力契约版本。任何一项不满足，都应在扩展中心明确显示原因并禁止启用。

兼容失败时按以下优先级处理：

```text
主题某个可选资源缺失 → 用内置资源补齐
某一页面模板无效      → 该页使用内置模板
主题核心清单/签名无效  → 禁止激活整个主题
激活后渲染自检失败     → 原子恢复到上一个主题
连续启动失败           → 启动进入内置安全主题并显示诊断
```

这套回退策略是让“可替换界面”可以交付到真实设备的前提，而不是附加功能。
