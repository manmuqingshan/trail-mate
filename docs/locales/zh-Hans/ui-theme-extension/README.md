# Trail Mate 可替换界面主题扩展方案

## 文档定位

本目录是一组中文的**讨论稿**，用于确定 Trail Mate 固件的“前后端分离”改造边界：固件保留全部业务能力、权限、设备访问和导航语义；用户或第三方安装的主题包只替换图标、视觉令牌和经过约束的页面布局。本文档不包含固件实现，也不改变当前运行行为。

第一条不可变的产品规则是：**当前仓库中的现有界面就是 Trail Mate 的出厂默认界面（逻辑 ID：`builtin.default`）**。但“内置”描述产品归属，不描述资源存储位置：默认主题的图标、视觉令牌、布局二进制和资源索引应随出厂 FFat 镜像写入内部 Flash 的 FFat 分区，而不是编译为 C/C++ 资源塞进应用固件镜像。固件镜像保留能力、路由、动作、渲染器和主题加载器。

启动时先挂载 FFat 并加载 `builtin.default`；之后才尝试从 SD 选择用户安装的主题覆盖层。没有 SD、没有安装主题、外部主题不兼容/损坏、主题启用失败或用户选择“恢复默认”时，设备使用 FFat 中的出厂默认主题。若 FFat 无法挂载、资源损坏或与固件契约不匹配，则进入独立的固件内 `rescue` 恢复呈现，供用户诊断、重新刷写 FFat 或恢复系统；它不是完整默认主题，也不携带完整图标/布局资源。

## 适用设备与完整性规则

本讨论稿仅覆盖 ESP32 下的 Trail Mate 固件。完整设备矩阵包括 Tab5、T-Display P4 TFT、T-Display P4 AMOLED、T-LoRa Pager（SX1262/LR1121）、T-Deck、T-Watch S3、T-Deck Pro（A7682E/PCM512A）。每个 target/profile 都必须有能力目录、FFat `builtin.default` 资源变体、SD 主题兼容规则、输入/内存预算和实机验证证据。Linux、nRF52、Cardputer 与其他非 ESP32 平台明确不属于本次改造、测试或交付范围。

“完整”约束固件架构和官方默认主题：启动、菜单、仪表盘、所有 AppCatalog/`PageKind` 页面、设置/蜂窝子页面、表盘、屏保、顶栏、通知、输入、确认、overlay、故障回退都必须纳入契约与资源清单。第三方主题可以只声明适配的 ESP32 profile；但它在每个已声明 profile 中必须覆盖该 profile 的完整 route 集合，不能通过遗漏页面形成混合 UI。

当前仓库已经存在三项可复用基础：

- `Extensions` 页面及其包目录、安装、卸载和状态呈现能力；
- 面向 locale/content/input bundle 的远程目录、下载、SHA-256 校验、解压和已安装索引；
- `ui_lvgl_ux_packs` 中按目标设备选择屏幕集合、输入绑定和布局配置的 UX Pack 机制。

因此，本方案不是另起一套插件系统，而是在现有包管理能力之上增加受限的 `theme-bundle`，并把现有固件页面沉淀为稳定的“能力契约”。

## 本轮希望先达成的结论

在开始实现前，请优先确认以下原则是否符合产品意图：

- 主题包是**无代码、声明式**资源包；不加载 ELF、动态库、Lua/JS/WASM，也不执行主题作者的脚本。
- 当前界面固化为 `builtin.default`，其完整资源位于 FFat 出厂分区，不安装到 SD，也不允许用户卸载或覆盖；FFat 无法使用时进入独立固件内 `rescue` 恢复呈现，提供固定诊断与恢复入口。
- 外部主题包下载/侧载后解压至 SD 的 `/trailmate/packs/themes/<theme-id>/`；固件只从已安装索引指向的主题目录加载 `theme.ini`、`theme.tmb` 和资源索引，不直接从 ZIP 或作者源文件加载。
- 设备端主题路径**不解析 JSON**，也不把不可信文件构造成 `std::string`、`std::vector` 或 cJSON 对象树；安装索引、活动状态、远程目录和资源索引均采用固定上限的二进制记录与流式读取。
- 目标设备的 UX Pack 决定哪些能力可以出现；主题包不能新增、移除、隐藏或改变能力的可达性。
- 页面能力以稳定的 `capability_id`、`route_id`、`action_id` 和 `slot_id` 对外暴露；主题只对这些稳定键绑定资源和布局。
- 主题源码位于仓库根 `themes/`，与 `packs/` 分离；每一个 ESP32 `target_profile_id` 都具有独立的 `builtin.default` 源目录、FFat 映像输入、主题包和预览页面，不允许以布局宏在设备间复用坐标树。
- 主题安装后先校验，只有完整通过后才允许激活；激活失败或渲染异常会自动回退到内置主题。
- 第三方主题通过 `themes/community/` 的 Pull Request 进入当前工程；PR CI 只校验，受保护主分支上的 CI 才构建、签名并发布主题目录、Release 附件和 GitHub Pages 详情页。本地侧载仍受相同格式、签名和兼容性验证约束。

## 术语

| 术语 | 含义 |
| --- | --- |
| 能力（Capability） | 固件可向用户提供的一项稳定业务能力，例如“发送聊天消息”“安装扩展包”。 |
| 能力契约（Capability Contract） | 主题可依赖的、版本化的页面状态、动作、组件槽位和可访问性要求。 |
| 路由（Route） | 用户可进入的界面状态，例如 `chat.conversation`、`extensions.confirm_install`。 |
| 动作（Action） | 由固件定义并执行的意图，例如 `chat.send`、`settings.apply`。 |
| 槽位（Slot） | 主题可布局的、语义固定的组件位置，例如 `chat.compose.send`。 |
| UX Pack | 现有的、随固件编译的设备产品策略；决定页面集合、输入方式、功能深度与设备布局。 |
| 主题包（Theme Bundle） | 可下载的、无代码的扩展包；只提供视觉资源、令牌和布局描述。 |
| 内置主题 | 固件随版本发布、永远存在的安全回退呈现。 |

## 方案状态

所有字段名、目录名和命令行名称均为拟议 API。在以下文档完成评审并冻结第一个 `theme_api` 版本前，不应将它们视为已实现接口。特别是 [实现前必须冻结的详细设计](./09-实现前必须冻结的详细设计.md) 中列出的阻断项，任何一项没有明确决定、负责人和验证证据时，都不得开始对应固件实现。
