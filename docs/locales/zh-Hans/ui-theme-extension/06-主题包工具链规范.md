# 06：主题包工具链规范

## 工具的责任

拟新增的 `tools/theme_pack.py` 是主题格式的唯一官方构建入口。它应使第三方在主机上完成昂贵且复杂的工作：Schema 校验、布局编译、资源转换、预算估算、归档规范化、哈希、签名与模拟验收；固件只需要加载已经严格约束的产物。

工具不是运行时能力：它不进入固件、不随主题归档携带，也不在设备上执行。

## 命令总览

| 命令 | 输入 | 输出 | 作用 |
| --- | --- | --- | --- |
| `init` | 主题 ID、名称、SDK 版本 | 作者工程骨架 | 建立完整、可验证的主题项目。 |
| `validate` | 作者工程 + SDK | 文本/JSON 诊断报告 | 不生成产物地检查清单、Schema、槽位、资源、预算和兼容性。 |
| `build` | 作者工程 + SDK + 一个 `target_profile_id` | 一个 profile 专属 `.tmt`、构建报告、文件哈希 | 编译该 profile 的布局、转换图标、生成索引和规范化归档。 |
| `inspect` | `.tmt` | 人可读报告 | 列出清单、资源、哈希、布局统计、目标和兼容性。 |
| `test` | `.tmt` + ESP32 target/profile | 路由测试报告、截图、可达性报告 | 驱动官方样例能力视图，覆盖每个声明 profile 的完整 route 集合。 |
| `sign` | 已构建 `.tmt` + 受保护签名代理 | 带签名的 `.tmt` | 仅受信任发布 CI 使用，签署规范哈希清单且不暴露私钥。 |
| `verify` | `.tmt` + 公钥/信任库 | 验证报告 | 离线复算哈希并验证签名、归档结构和 Schema。 |
| `catalog` | 一组已验证 `.tmt` | 目录条目/目录签名输入 | 供发布端生成扩展目录，设备端不运行该命令。 |

命令名称可在实现前微调，但每项职责必须保留，以保证制作流程可复制、可审计。

## 建议的命令行接口

```powershell
# 创建工程
python tools/theme_pack.py init --id acme.forest --name "Forest Field" --api 1.0

# 本地开发期检查
python tools/theme_pack.py validate --source C:\work\acme-forest --sdk tools\theme-sdk\1.0

# 可复现构建
python tools/theme_pack.py build --source C:\work\acme-forest --sdk themes\sdk\theme-api-1.0 --target p4_tft_touch --out dist --source-date-epoch 0

# 查看包，不安装也不执行包内内容
python tools/theme_pack.py inspect --package dist\acme.forest-0.1.0-p4_tft_touch.tmt --format markdown

# 对某个目标执行完整路由/可访问性验收
python tools/theme_pack.py test --package dist\acme.forest-0.1.0-p4_tft_touch.tmt --target p4_tft_touch --all-routes

# 仅在受保护发布 CI 中签名；第三方作者不执行此命令，也不拥有签名私钥
python tools/theme_pack.py sign --package dist\acme.forest-0.1.0-p4_tft_touch.tmt --key-id trailmate-release-2026 --signer protected-ci
```

## `validate` 必须检查的内容

### 发布元数据

- `package.ini` 必须存在，类型为 `theme-bundle`，ID 符合命名规则，SemVer 合法；
- `theme_api`、`capability_contract`、最低固件版本和 SDK 版本相容；
- 支持 target/profile、UX Pack、显示类别、输入模型和预算 ID 都来自 SDK；
- 作者、许可证、描述和变更信息达到公开目录要求；
- 同一目录内不允许重复 ID、重复资源键或覆盖保留内置主题 ID。

### 能力契约

- 每个声明 target/profile 都导出相应的完整可用路由；
- 每个覆盖布局都引用已发布的 `route_id` 和 `slot_id`；
- 必需槽位一次且仅一次，可选槽位不跨路由滥用；
- 动作槽位与动作类型相容，危险动作仍在确认语义内；
- 布局树没有循环、未知容器、非法嵌套、超深层级或超过节点上限；
- 键盘/编码器目标通过焦点可达性；触控目标通过 profile 规定的命中区要求；
- 本地化字符串、长文本、RTL 和缺失可选数据可安全排版；
- 壳的 `Back` 与安全模式入口不被主题布局覆盖。

### 资源与预算

- 资源只来自允许扩展名、允许目录和 `assets.index` 声明；
- SVG 在主机转换时禁止外部文件、网络引用、脚本、滤镜炸弹和超大路径数据；
- PNG/图标的像素数、色深、动画帧数、压缩比和解码估算内存均按目标 profile 预算检查；动画只能使用格式规范明确允许且经固件实现的帧序列。
- 字体与 locale/font pack 的职责不冲突，未声明的文本覆盖字体不允许打包；
- 总归档、解压后总量、单文件、单图、资源数量、布局节点数均按每个目标预算检查；
- 预览资源与运行时资源分别计量，不能用预览图绕过大小限制。

### 安全结构

- ZIP 文件名必须规范化；拒绝绝对路径、`..`、反斜杠歧义、重复规范路径、符号链接和设备文件；
- 拒绝嵌套归档、可执行格式、脚本文件和不在白名单中的 MIME 类型；
- 所有归档文件有哈希，归档条目按字节序规范排序；
- 如要求签名，必须验证 key ID、签名算法、签名覆盖范围和撤销状态；
- 生成诊断时只输出相对路径和非敏感元数据。

## `build` 的确定性产物

`build` 的理想行为应是：同一源、同一 SDK、同一参数，在不同机器上产生相同的 `theme.tmb`、资源字节、文件哈希和 `.tmt`。为此工具应：

1. 使用版本锁定的图标转换器和布局编译器；
2. 固定 SVG/PNG 正规化、色彩空间、图像尺寸、压缩参数和资源排序；
3. 将 `theme.yaml` 转为确定性的 `theme.tmb`，不将绝对路径、机器名、当前时间写入内容；
4. 用 `SOURCE_DATE_EPOCH` 或等价明确参数控制归档时间戳；
5. 生成 `assets.index`、`manifest.sha256`、尺寸与预算报告；
6. 只把归档白名单中的文件写入 `.tmt`；
7. 构建后再执行一次与设备加载器相同语义的 `verify`。

构建报告可使用 JSON 作为**主机/CI**输出，同时打印简短文本摘要：主题 ID/版本、唯一 `target_profile_id`、归档大小、解压大小、各资源内存估算、布局节点数、完整 route 覆盖结果、动作/焦点可达性结果和 SHA-256。报告 JSON 不属于 `.tmt` payload，也不进入 ESP32 Theme Runtime。

## `theme.tmb` 二进制格式要求

二进制格式的具体字节布局应在实现时另立格式规范，但至少必须具备：

- 固定 magic、格式主/次版本、字节序和总长度；
- 头部 CRC 或哈希，记录表偏移量均经过范围检查；
- 字符串表使用长度前缀，单字符串长度受限；
- `route_id`、`slot_id`、`token_id`、`asset_id` 使用 SDK 分配的整数表或严格映射；
- 节点记录只使用有限枚举与定宽/有界字段；
- 不存储原始 YAML、JSON、正则、脚本、表达式或任意字符串键；
- 支持流式读取和失败关闭；遇到未知关键枚举、长度溢出、引用越界、循环或预算超限立即拒绝。

在主版本未冻结之前，工具不应将此格式标为公开稳定 ABI。对第三方开放时，应同时发布格式测试向量和错误码表。

## `test` 的验收模型

工具应使用固件导出的样例 `CapabilityView` 和每个 target/profile 的路由集合运行主题，不需要读取用户真实数据。测试至少产生：

- 每个可用 `route_id` 的布局构建结果；
- 必需槽位、动作、焦点和返回路径可达性结果；
- 正常、加载、空数据、错误、离线、长文本、RTL、低存储等状态的截图或结构快照；
- 危险确认页是否仍同时具有取消和确认入口；
- 内存/节点/资源加载峰值与预算比对；
- 声明 target/profile 的完整 route 覆盖清单；任一缺页、缺必需 slot 或缺输入/确认路径均为失败。

下列场景以及每个 profile 的其余 route 均列为阻断性失败检查：聊天编辑、设置编辑、Extensions 安装确认、恢复内置主题、设备关机确认（若目标有）、无线/维护确认（若目标有）、蜂窝确认（若目标有）、表盘/唤醒（若目标有）和全局返回。

## CI 与发布集成

主题仓库/目录的 CI 应至少运行：

```text
validate
  → build（确定性构建两次并比较哈希）
  → verify
  → test（全部声明支持的 target/profile）
  → 签名验证
  → 生成目录条目
```

Trail Mate 固件 CI 还应运行“内置主题 + 官方样例主题”矩阵，以保证新增的能力契约、页面或动作不会无意破坏已发布主题。

主题作者在 Pull Request 中只调用 `validate`、`build`、`inspect`、`test` 和 `verify`。`sign`、`catalog`、Release 上传和 GitHub Pages 部署仅由受保护分支的 CI 调用；这避免 fork PR 接触发布机密或修改公共设备目录。完整工作流见 [第 15 篇：主题 PR、CI 与 GitHub Pages 发布协议](./15-主题PR、CI与GitHubPages发布协议.md)。

## 工具实现的边界

- 工具可使用 Python 和主机图像转换依赖；最终实现需锁定版本、依赖哈希和受支持的作者主机环境。
- 工具不得要求连接真实设备才可进行基础 `validate` 与 `build`。
- 工具不得自动上传、发布或修改远程目录；发布仍是用户明确授权的独立流程。
- 工具不得从主题工程执行外部命令、`npm install`、脚本钩子或任意插件。图标转换器只能是工具自身受控依赖。
- 工具产生的包必须能由纯固件验证器独立拒绝错误输入，不能把安全性建立在“作者已运行工具”之上。
