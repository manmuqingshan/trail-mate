# 14：工程目录与独立默认主题规划

## 结论：主题是仓库中的一等源代码资产，不是固件资源的旁路目录

主题系统完成后，Trail Mate 仓库必须同时保存三类彼此分离、可追溯的内容：

1. **ESP32 固件主题运行时**：能力契约、二进制 reader、FFat/SD provider、受限 renderer、安装事务和 target/profile resolver；
2. **主题作者源工程**：每个 ESP32 target/profile 的完整布局、资源、预览、说明、测试与许可证；包括官方出厂默认主题和经审核的第三方主题；
3. **CI 生成物**：FFat factory image、目标专用 `.tmt`、设备二进制目录、浏览器目录、截图和 GitHub Pages 静态详情页。

三者必须分开。源工程由 Git 管理并通过 Pull Request 审核；生成物由 CI 生成、验证、签名和发布；设备只读取经安装器提交到 SD 的二进制 payload，或 FFat factory root 中的 `builtin.default`。任何主题都不能以 C/C++ 宏、编译进应用的 `lv_image_dsc_t`、直接 LVGL 回调或预处理器条件来决定运行时布局。

## 1. 对现有仓库结构的判断

当前 [packs/](../../../../packs/) 与 [scripts/build_pack_repository.py](../../../../scripts/build_pack_repository.py) 服务 locale/font/IME 包，当前 [site/](../../../../site/) 和 [`.github/workflows/pages.yml`](../../../../.github/workflows/pages.yml) 负责 GitHub Pages。它们是可复用的发布基础，但**不是主题源的放置位置**：

- `packs/` 的设备内容、`installed.json` 兼容路径和浏览器 `packs.json` 面向语言/字体/输入包；主题必须使用独立的 `TMIX`/`TMTS`、`theme.tmb`、`assets.index` 与二进制主题目录，不能混写或复用 JSON 设备读取模型。
- `site/` 是 Pages 静态站点的源码根与工作目录；它可以承载主题浏览页，却不能成为主题的唯一源工程，更不能保存主题作者可编辑的运行时 payload。
- `modules/ui_shared/src/ui/assets/`、`images.h`、`ui_theme.h` 是当前编译期视觉资源的来源。迁移完成后，它们不再是普通 ESP32 页面使用的主题资源根；FFat factory theme 和 SD provider 才是资源根。

因此新增的 `themes/` 是仓库的唯一主题源根，和现有 `packs/` 并列。主题构建器、Pages 构建器和 FFat 镜像构建器都只从该根读取经审核的内容。

## 3. 主题源的统一内部结构

`themes/factory/builtin.default/`、`themes/official/<theme-id>/` 和 `themes/community/<publisher-id>/<theme-id>/` 使用同一结构。差异仅是发布者治理和信任等级，不是格式分叉。

```text
<theme-source-root>/
├── package.ini                 # 身份、作者、许可、版本、发布元数据
├── DESCRIPTION.md              # GitHub Pages 详情正文，受限 Markdown
├── CHANGELOG.md
├── LICENSE.txt
├── theme-source.yaml           # 主题家族声明：每个 profile 的来源与覆盖级别
├── profiles/
│   └── <target-profile-id>/
│       ├── theme.yaml          # 该设备唯一的 token、layout、widget 容器声明
│       ├── assets-src/         # SVG/PNG 等作者源资产，仅主机工具读取
│       ├── fonts-src/          # 允许的字体作者源；按协议转换
│       ├── previews/
│       │   ├── cover.png
│       │   └── <route-id>.png
│       ├── screenshots.yaml    # route/state → 预览/验收截图映射
│       ├── accessibility.yaml  # 对比、替代文本、输入可达性说明
│       └── tests/
│           ├── expected-routes.yaml
│           └── visual-baseline/
└── shared/                     # 只允许主机阶段显式复制的公共源资产/文案
```

### 3.1 `profiles/<target-profile-id>/` 是独立默认主题的核心

每个 profile 目录是一个完整主题单元，不是“同一份布局加若干宏”。例如 P4 AMOLED 可以采用深色 OLED 视觉与资源格式，Pager 可以采用高对比紧凑焦点布局，T-Deck Pro 可以采用独立的单色行式信息架构，T-Watch 可以使用表盘/通知优先布局。它们不要求共享 YAML、坐标、容器树、颜色 token 或图标集。

`shared/` 只允许保存经过显式引用的许可证文本、品牌源图、共同说明或经工具复制的原始资产；它**不得**包含跨 profile 的 `#if`、`ifdef`、预处理布局片段、设备判断表达式或可在设备上执行的条件逻辑。一个 profile 的 `theme.yaml` 只能包含那个 profile 的静态受限布局。

这条规则直接替代现有“通过宏控制同一布局”的模式：

| 维度 | 改造前常见做法 | 改造后的固定做法 |
| --- | --- | --- |
| 设备选择 | `#if`、编译宏、散落的宽高判断决定坐标/对象树。 | 固件启动先解析 `Esp32TargetThemeProfile`；Theme Runtime 打开该 profile 对应的 FFat/SD payload。 |
| 默认视觉 | C/C++ 图标、颜色函数和页面常量随应用编译。 | 每个 profile 的完整默认主题源经 CI 编译到对应 FFat factory image。 |
| 布局差异 | 一个页面的多处分支逐渐难以覆盖。 | 每个 profile 有自己的 `theme.yaml` 与 route 完整性报告。 |
| 第三方适配 | 作者猜宏、屏幕尺寸和编译符号。 | 作者选择一个或多个稳定 `target_profile_id`，每个目录独立制作、验证和发布。 |

宏仍可用于固件的**编译能力选择**，例如板级驱动、PSRAM、蜂窝功能、输入外设或 FeatureFlags；它们只能影响 `CapabilityRegistry` 输出哪些 route/action，不能成为普通视觉布局、图标或页面坐标的来源。

### 3.2 `builtin.default` 的身份与独立性

设备侧仍把 FFat trusted fallback 识别为逻辑主题 ID `builtin.default`，以保持恢复、状态记录和用户界面语义稳定。仓库中 `builtin.default/profiles/<target-profile-id>/` 的每个目录却是可独立设计、构建、验收和发布的 factory variant。

也就是说：

```text
设备逻辑身份：builtin.default
FFat 选择键：target_profile_id + factory generation + contract hash
仓库主题源：builtin.default/profiles/<target-profile-id>/theme.yaml
```

这不会把所有设备锁进同一种视觉设计；它只让所有设备在 FFat 故障回退、Extensions“恢复默认”和更新配对中使用同一个受信逻辑身份。

## 4. 一个主题源如何生成目标专用设备包

作者可以在一个主题家族中声明多个 profile，但 CI 不产生包含所有设备资源的通用归档。构建命令以 profile 为单位生成设备 payload：

```text
themes/community/acme/acme.forest/
  ├─ profiles/p4_tft_touch/
  ├─ profiles/p4_amoled_touch/
  └─ profiles/twatch_compact/

theme_pack.py build --theme acme.forest --target p4_tft_touch
  → build/themes/archives/acme.forest/0.3.0/p4_tft_touch/acme.forest-0.3.0-p4_tft_touch.tmt

theme_pack.py build --theme acme.forest --target twatch_compact
  → build/themes/archives/acme.forest/0.3.0/twatch_compact/acme.forest-0.3.0-twatch_compact.tmt
```

每个 `.tmt` 只包含一个 `target_profile_id` 所需的 `theme.ini`、`theme.tmb`、`assets.index`、资源和字体。安装器以 `theme_id + version + target_profile_id + archive_sha256` 识别版本；设备不会下载或存储其他设备的资源。GitHub Pages 以主题家族聚合展示这些目标专用产物，用户先选择自己的设备 profile，再看到可安装版本。

这要求更新 [03：主题包格式与固件接口](./03-主题包格式与固件接口.md) 中的分层定义：

- **作者源 `package.ini`/`theme-source.yaml`** 可以声明多个 profile；
- **CI 生成的设备 archive `package.ini`** 必须只有一个 `target_profile_id`，并记录源主题 ID、版本、contract hash、factory/社区发布者和 archive hash；
- **FFat factory image** 同样只封装当前 ESP32 target 的 `builtin.default` variant；
- **GitHub Pages 浏览器目录** 可以聚合多个 profile，因为浏览器不是 ESP32 Theme Runtime；
- **设备目录** 按 profile 发布签名 `TMCP` 二进制页，不能下载浏览器 JSON 后在设备解析。

## 5. 固件侧目录和页面改造的对应关系

`modules/ui_theme_contract` 与 `modules/ui_theme_runtime` 只由 ESP32 启动/页面路径链接。它们不会被 Linux/nRF52 target 引入。页面不需要迁入一个巨型“主题目录”；业务仍留在当前模块，页面迁移时在原页面附近新增 Presenter adapter。

| 当前区域 | 新增/调整位置 | 目录职责 |
| --- | --- | --- |
| `apps/esp32_lvgl` 启动 | `esp32_lvgl_theme_bootstrap.*`、`esp32_lvgl_target_theme_profile.*` | 在创建旧菜单前解析 target/profile，验证 FFat，选择 provider，建立 Shell Renderer。 |
| `modules/product_composition` | target/profile/UX binding 定义 | 让 Tab5、P4、Pager、T-Deck、T-Watch、T-Deck Pro 都有正式稳定 identity。 |
| `modules/ui_shared/src/ui/screens/<page>` | `<page>_presentation_adapter.*` | 导出脱敏 ViewModel、固定 action；移出 LVGL 视觉树、C++ icon 和直接色板。 |
| `modules/ui_mono/.../screen_240x320` | `mono_theme_presentation_adapter.*` | 为 T-Deck Pro 的 PageKind/蜂窝页提供独立 mono ViewModel 和 Theme Renderer 接口。 |
| `modules/ui_theme_contract` | descriptors 与 export | 汇总完整 route/slot/action，导出 SDK 与二进制 fixture。 |
| `modules/ui_theme_runtime` | provider/reader/renderer/installer/rescue | 实现 FFat、SD、二进制主题、完整回退和事务；不包含业务代码。 |
| `platform/esp` | ESP 文件系统、签名、网络/下载适配 | 提供 SD/FFat 句柄、热拔插和网络传输；不解释主题 layout。 |

逐页源文件与 Presenter 的完整映射仍以 [13：当前 UI 源码盘点与解耦改造地图](./13-当前UI源码盘点与解耦改造地图.md) 为准。本文件补的是“新文件应落在哪里、如何避免主题源/生成物/运行时混放”的结构约束。

## 6. 禁止提交和允许提交的内容

| 内容 | 是否允许进入主题 PR | 原因 |
| --- | --- | --- |
| `package.ini`、`theme-source.yaml`、profile `theme.yaml` | 允许 | 它们是可审查的主题声明源。 |
| SVG/PNG/字体作者源、许可证、说明、预览源、测试期望 | 允许 | 必须可追溯版权、可复现转换与人工审查。 |
| `theme.tmb`、`assets.index`、`.tmt`、FFat image、签名 | 不允许 | 它们由受控 CI 从 PR 源构建、签名和发布。 |
| 任意脚本、二进制、动态库、Node/Python hook、第三方工具锁文件 | 不允许作为主题内容 | 主题作者不能让 CI 或设备执行其自定义代码。 |
| 修改 `themes/sdk/`、`themes/policy/`、target profile 定义 | 需要核心维护者审批 | 这会扩大作者 API 或改变设备兼容性。 |
| 修改 `modules/`、`platform/`、`apps/` 固件代码 | 不属于“提交一个主题”的普通权限 | 必须走独立固件设计、影响分析与代码审查。 |

## 7. 工程结构的验收条件

目录规划只有同时满足以下条件才算完成：

- [ ] `packs/` 与 `themes/` 的设备格式、索引、构建器和 Pages 目录已分离；主题运行时没有调用旧 locale 包的 JSON API。
- [ ] 每个 ESP32 target/profile 都有 `builtin.default/profiles/<profile>/` 源、FFat image 产物和完整 route 报告。
