# 13：当前 UI 源码盘点与解耦改造地图

## 给刚接手项目的人：先理解“当前界面”是什么

Trail Mate 当前不是“后端提供数据，前端读取模板”的应用。它是一个运行在 ESP32 上、以 LVGL 为显示框架的固件：一个页面文件往往同时创建 LVGL 对象、决定图标/颜色/坐标、响应触控或按键、读取业务状态、执行动作、启动定时器并清理资源。对用户而言，这些代码合起来就是当前出厂界面；对主题系统而言，它们是必须逐项拆开的耦合点。

本方案要把“怎么画”从“能做什么”中剥离，边界如下：

- 固件继续拥有全部业务能力、硬件访问、状态机、导航、权限、危险操作确认、输入协议和数据脱敏；
- 当前界面的**完整默认资源和默认布局**以 `builtin.default` 的形式放入 FFat 出厂镜像，而不是放在应用固件镜像中；
- 用户下载、侧载和安装的第三方主题只存放在 SD；它们只能替换经契约批准的图标、字体、设计令牌和布局树；
- 主题只能引用固件导出的 `capability_id`、`route_id`、`slot_id`、`action_id` 和内建 widget，不能引入新能力、脚本、回调、URL、网络访问或任意 LVGL/C++ 对象；
- SD 主题错误时回退 FFat `builtin.default`；FFat 无法验证或无法读取时进入独立 `rescue` 恢复呈现。`rescue` 具备固定诊断和维护入口，但不依赖 FFat、SD 或主题包。

本文回答实现前不能跳过的问题：**当前 ESP32 UI 从哪里启动？每个可见页面对应哪些文件？视觉、业务和输入在哪里耦合？哪些文件必须解耦，哪些职责必须保留在固件？**

本文是设计证据和改造地图，不进行任何固件修改。下文的“拟新增”“拟迁移”“拟替换”描述的是要冻结的目标边界，不表示相应目录或类已经存在。

## 1. 范围、证据口径和 ESP32 完整目标矩阵

### 1.1 本文的范围

本文只覆盖 ESP32 下的构建、启动、运行和用户可见 UI。具体包括：

- `apps/esp32_lvgl` 的 ESP-IDF 与 Arduino/PlatformIO 启动和应用注册路径；
- `modules/ui_shared` 中对 ESP32 可见的 LVGL shell、页面、组件、overlay、图标、字体和颜色；
- `modules/ui_mono` 的 `screen_240x320` 与蜂窝相关页面；
- `modules/ui_lvgl_ux_packs` 中由 ESP32 target/profile 选用的屏幕集合与输入规则；
- ESP32 上 Extensions、主题下载、SD 安装、FFat 默认主题加载所需的运行时边界。

Linux 模拟器、Linux uconsole、Cardputer、nRF52 和其他非 ESP32 平台明确不在本方案授权范围内。它们不列入本文件的迁移、测试、FFat 镜像、主题 SDK 兼容性或发布承诺；也不能用作 ESP32 验收结论的替代证据。

### 1.2 证据如何阅读

| 标记 | 含义 |
| --- | --- |
| **现有顶层应用** | 当前 `AppCatalog` 或 `PageKind` 已存在的稳定页面入口，例如 `chat`、`settings`。 |
| **现有呈现面** | 用户实际可看到的列表、详情、编辑、确认框、浮层、状态屏、表盘或内嵌 widget；它不一定已有独立 `route_id`。 |
| **目标主题路由** | 将来能力契约中冻结的 `route_id`；在契约生成之前是拟议 API，不能反推 C++ 中已经存在同名对象。 |
| **保留在固件** | 业务、状态、权限、动作、输入、算法或安全规则；主题永远不能接管。 |
| **由主题提供** | 合法 layout、token、asset、字体选择和已注册 widget 的容器；必须经 Theme Runtime 校验。 |

### 1.3 ESP32 目标矩阵：每个目标都在完整覆盖范围内

`modules/product_composition/src/target_build_binding.cpp` 当前将 Tab5、两种 T-Display P4、T-LoRa Pager、T-Deck 和 T-Watch 绑定到 `builds/esp_idf` 与 `apps/esp32_lvgl`；`target_ux_binding.cpp` 继续为它们选择产品 profile 和 UX Pack。`platformio.ini` 还声明 T-LoRa Pager 两个无线变体、T-Deck、T-Watch S3 以及 T-Deck Pro 的 A7682E/PCM512A 变体。下表把这些事实和主题改造要求放在一起。

| ESP32 设备/变体 | 当前构建或启动证据 | 当前 UX/profile 事实 | 主题系统的完整要求 | 实现前必须修复/冻结的事实 |
| --- | --- | --- | --- | --- |
| Tab5 | [target_build_binding.cpp](../../../../modules/product_composition/src/target_build_binding.cpp)、[esp32_lvgl_runtime_config.cpp](../../../../apps/esp32_lvgl/src/esp32_lvgl_runtime_config.cpp) | `tab5_touch` 产品 profile；当前绑定 `compatibility` UX Pack。 | 生成 FFat 默认主题、全部 capability/route、触控 layout、SD 主题校验与实机验收。 | 目标 ID、显示/输入参数、PSRAM 与资源预算由统一 `Esp32TargetThemeProfile` 输出。 |
| T-Display P4 TFT | 同上；[target_profiles.cmake](../../../../builds/esp_idf/target_profiles.cmake) | `t_display_p4_touch`，IDF 运行时已有 P4 target 解析。 | 覆盖全部大屏 AppCatalog、全局 shell、地图/GNSS、设置、Extensions、overlay 与故障路径。 | 记录 TFT 特定色深、方向、触控、缓存和 FFat 镜像预算。 |

| T-Watch S3 | [platformio.ini](../../../../platformio.ini)、[target_build_binding.cpp](../../../../modules/product_composition/src/target_build_binding.cpp) | `watch_compact`，当前绑定 `compatibility` UX Pack；另有 watch/chat-watch 源码。 | 覆盖表盘、聊天手表投影、通知、休眠/唤醒、窄屏 shell、全部可达 route。 | 把 `watch_face.cpp`、`chat_watch/` 与通用目录一起导出契约和 FFat 资源。 |

**结论**：所有上表 ESP32 目标均属于本方案的完整交付范围。第三方主题可以只声明自己适配的一组 profile；但每个官方 `builtin.default`、Theme Runtime、能力目录、Extensions 流程与验收体系必须覆盖全表。不存在以 P4 成功为由省略 Pager、T-Deck、T-Watch 或 T-Deck Pro 的发布条件。

### 1.4 当前 target 解析存在的两处缺口

1. [esp32_lvgl_runtime_config.cpp](../../../../apps/esp32_lvgl/src/esp32_lvgl_runtime_config.cpp) 当前仅对 Tab5 与两种 P4 明确解析 target identity；其他 IDF 目标会落入通用 `esp_idf` 结果。主题选择不能根据这一通用字符串猜 profile，必须由新的统一 resolver 返回严格的 target ID、显示/输入 profile、UX Pack ID、FFat/SD capability 和预算 ID。
2. [esp32_lvgl_arduino_startup_runtime.cpp](../../../../apps/esp32_lvgl/src/esp32_lvgl_arduino_startup_runtime.cpp) 当前构造 `startup_shell::Hooks` 时没有像 [esp32_lvgl_startup_runtime.cpp](../../../../apps/esp32_lvgl/src/esp32_lvgl_startup_runtime.cpp) 一样传递 `ux_pack_id`。必须先统一两条启动路径，Theme Runtime 才能用同一规则校验主题 manifest。

这两项是“编码前必须冻结”的真实缺口，而不是可以靠文档默认值掩盖的问题。

## 3. 从开机到用户动作：当前路径与目标路径

### 3.1 当前路径（以 P4 打开 Extensions 为例）

```text
ESP32 启动运行时
  └─ buildShellHooks(): AppCatalog + 当前 UX Pack
      └─ startup_ui_shell::initializeMenuSkeleton()
          ├─ buildMenuForUxPack(): 编译期 UX Pack 产生屏幕集合
          ├─ menu_layout::init(): 创建 LVGL 菜单、图标、颜色和像素布局
          └─ menu_runtime::init(): 处理焦点、时间、电量、快捷键、屏保
              └─ 用户选择 AppScreen(stable_id = "extensions")
                  └─ CallbackAppScreen::enter()
                      └─ extensions::ui::shell::enter()
                          └─ extensions::ui::runtime::enter()
                              └─ 创建列表、详情、筛选、进度和确认 UI
                                  └─ 调用目录、下载、安装与卸载能力
```

现有层级并非没有职责划分，但边界仍不完整：应用目录含视觉图标，页面 runtime 含视觉布局，组件含动作和业务调用。因此不能让主题包“接管 LVGL”；那会迫使主题复制业务代码，或赋予主题不应拥有的权限。

### 3.2 目标路径

```text
Esp32TargetThemeProfile + UX Pack + FeatureFlags
  └─ CapabilityRegistry
      └─ 输出当前设备可用的 capability / route / action / slot 集合
          └─ ThemeRuntime 选择 FFat builtin.default 或经验证的 SD ThemeProvider
              └─ ThemeLayoutReader/Validator 读取受限二进制布局与资源索引
                  └─ PagePresenter 导出脱敏且有界的 ViewModel
                      └─ ThemeRenderer 创建允许的 LVGL 节点及已注册 widget
                          └─ 固件 ActionDispatcher 执行固定 action_id
```

该路径中，主题文件只回答“该能力集合如何排列、使用哪个 asset/token”；它不读取服务、文件、密钥或网络，不决定哪些能力存在，也不解释业务命令。

## 4. 已确认的耦合证据

### 4.1 AppCatalog 同时绑定身份、图标和回调

[app_screen.h](../../../../modules/ui_shared/include/ui/app_screen.h) 要求 `icon()` 返回 `lv_image_dsc_t*`；[callback_app_screen.h](../../../../modules/ui_shared/include/ui/callback_app_screen.h) 的对象同时接收稳定 ID、名称、编译期图标和 LVGL 页面进入/退出回调。[app_catalog_builder.cpp](../../../../modules/ui_shared/src/ui/app_catalog_builder.cpp) 因而同时声明 `chat`、`map`、`settings` 等能力身份，引用 `Chat`、`gps_icon`、`Setting` 等 C 资源，并直接连到页面 `shell::enter`。

解耦要求：把稳定 ID、能力可用性、启动参数与 action 入口保留为固件 `CapabilityDescriptor`；把菜单名称本地化键、图标 asset key、菜单排序、外观和 layout 转给 Theme Renderer。`AppScreen::icon()` 不得再成为普通主题路径的视觉来源。

### 4.2 默认颜色、图标和字体仍被编译进应用

[ui_theme.h](../../../../modules/ui_shared/include/ui/ui_theme.h) 直接返回 RGB 颜色；ESP UI 路径当前有大量 `ui::theme::*` 调用。[images.h](../../../../modules/ui_shared/include/ui/assets/images.h) 以及 `modules/ui_shared/src/ui/assets/` 下的 `.c` 文件提供编译期 `lv_image_dsc_t` 图标，[font_utils.cpp](../../../../modules/ui_shared/src/ui/assets/fonts/font_utils.cpp) 负责字体辅助。

解耦要求：日常 UI 的颜色、图标、字体和 layout resource 全部由 FFat/SD `IThemeProvider` 按 asset/token ID 打开。应用固件只保留 `rescue` 所需的诊断文本、几何和输入支持，不能藏有第二份完整菜单、图标、字体和布局资源。

### 4.4 旧包仓库的 JSON 路径不能进入主题运行时

[pack_repository_runtime.h](../../../../modules/core_sys/include/platform/ui/pack_repository_runtime.h) 的目录接口使用 `std::vector<PackageRecord>`；ESP 实现 [pack_repository.cpp](../../../../platform/esp/arduino_common/src/ui/runtime/pack_repository.cpp) 使用 cJSON 与 `installed.json` 构造对象树和包数组。它可以继续服务 locale/content/input 等既有包的兼容路径。

主题系统必须另建 `theme_repository_runtime`、二进制目录分页读取、`theme-index.a/b`、`theme-state.a/b`、流式 asset reader 和固定记录格式。Theme Runtime 不允许通过 `fetch_catalog(std::vector<PackageRecord>&, ...)` 读取主题。

### 6.1 对这些页面的统一迁移规则

每个页面至少要形成以下可审计链条：`CapabilityDescriptor → RouteDescriptor → PagePresenter → 脱敏 ViewModel → Layout/slot 验证 → ThemeRenderer → 固件 ActionDispatcher`。这不是要求每页重复实现一个 renderer；一般页面共享 `ThemeRenderer`，地图/GNSS/设置编辑器等仅注册有限的固件 widget。

普通页面迁移完成前，它仍可用旧 LVGL 实现维持当前功能，但不能被标记为“主题可替换”，也不能让 Extensions 对该 profile 提供下载/启用主题的入口。对用户开放主题之前，所有本节页面必须完成迁移和验收。

## 11. 主题运行时必须冻结的完整接口边界

| 接口（拟议） | 输入 | 输出 | 明确禁止承担的责任 |
| --- | --- | --- | --- |
| `Esp32TargetThemeProfile` | 构建 target、面板、输入、PSRAM、文件系统 capability | 严格 target/profile/UX ID、预算、资源格式与输入规则 | 从主题 manifest 推断或改变硬件能力。 |
| `CapabilityRegistry` | UX Pack、FeatureFlags、硬件能力、构建期契约 | 有界的 capability/route/action/slot 描述 | 主题名称、图标、布局、下载或业务执行。 |
| `PagePresenter` | 业务状态、用户意图 | 脱敏且有界的 ViewModel、固定 action dispatch | `lv_obj_create`、颜色、图标文件、主题解析。 |
| `ThemeRuntime` | FFat Header、SD 双槽状态/索引、当前 route/profile | 已验证 provider、generation、回退结果 | 业务数据、目录 JSON、脚本/C++ 执行。 |
| `ThemeLayoutReader` / `ThemeAssetReader` | `.ini`、`theme.tmb`、`assets.index`、资源流 | 有界 PagePlan、asset handle/错误码 | 整文件读入、cJSON、全主题 `std::vector` 缓存。 |

## 12. 完整迁移与验收顺序

顺序只表达依赖关系，不能削减上述 ESP32 覆盖范围。

1. **先统一 target/profile**：补齐 T-Deck Pro 绑定，修复 IDF/Arduino 的 target 与 `ux_pack_id` 传递，生成完整 ESP32 target/profile 表。
2. **再导出能力契约**：覆盖第 5 至第 9 节所有呈现面、所有 AppCatalog/`PageKind` 页面、条件编译项、蜂窝页、表盘、输入和 overlay。
3. **建立可信资源通道**：实现 FFat factory image、`TMFH`、有界 reader、theme validator、provider、renderer、独立 rescue 和 Factory/SD 回退规则。
4. **迁移 shell 和所有页面**：每页先抽取 Presenter/ViewModel/Action 边界，再让 FFat `builtin.default` 经 ThemeRenderer 呈现；完成后才允许该页面的外部主题 layout。
5. **接入 Extensions 和 SD**：二进制 catalog/index/state、下载、安装、预览、激活、恢复默认、诊断、卸载和撤销，均对全 profile 生效。
6. **用工具和实机封闭验证**：每个 profile 的完整 route 清单、资源预算、焦点/触控、坏包、SD 热拔插、FFat 失效、掉电、App/FFat 更新和长期资源回收。
7. **开放第三方主题**：只在完整默认 UI、完整 reader/validator、完整 Extensions 生命周期和全 ESP32 证据均就绪后开放。

## 13. 评审者的完整性检查

- [ ] 第 1.3 节每个 ESP32 target/硬件变体都有正式 profile、UX Pack、目标解析、能力导出、FFat 默认主题、SD 主题兼容性和实机验证证据。
- [ ] Tab5、两种 P4、Pager 两种变体、T-Deck、T-Watch、T-Deck Pro 两种变体没有由另一个设备代替测试。
- [ ] 启动、菜单、仪表盘、屏保、表盘、顶栏、通知、busy/toast、IME、候选输入、配对、地图/通话浮层和 rescue 都有明确处理。
- [ ] 第 6 节每个 AppCatalog 项及 feature flag 条件项都有 Presenter、业务保留边界、theme route/slot 和 action 可达性测试。
- [ ] 第 7 节每个 `PageKind` 和蜂窝子页面都有 mono profile 模板、键盘焦点与资源预算；不存在“等到以后再处理”的空白。
- [ ] UX Pack 仍由固件决定，主题 manifest 只能声明兼容性，不能创建/移除 route 或重写应用可达性。
- [ ] 普通主题路径不再调用 `ui::theme::*`、`AppScreen::icon()`、`images.h` 或旧 JSON 包仓库 API；这些只可以服务非主题旧包兼容和 rescue 诊断。
- [ ] `settings`、`usb_mass_storage`、`energy_sweep`、`shutdown`、团队权限、蜂窝发信/拨号等危险动作仍有固件强制确认和可达性测试。

- [ ] Linux/nRF52 及其他非 ESP32 平台没有混入本方案的工作量估算、验收条件或支持声明。
